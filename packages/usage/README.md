# Usage capability (SET-1)

This private package owns the version 1 per-account usage contract, read-only provider adapters, the registered view ID `subset.usage.dashboard@1`, a structured agent result with a text fallback, and the shared Svelte dashboard view. The standalone host is the `subset-usage` CLI in `packages/usage-cli` (`@sub-set/usage`), which serves the view built from `apps/usage`. No public surface is released. External view inputs are validated with `isUsageStatus()` before the standalone host renders them.

## Supported local sources

| Provider | Source and operation | Multi-account boundary |
| --- | --- | --- |
| Codex / ChatGPT | Live read through documented local Codex app-server methods | One authenticated `CODEX_HOME` per account; browser connection is implemented |
| Claude Code | Last-collected Pro/Max quota from documented status-line JSON | Separate snapshot slot per account, optionally bound to its own `CLAUDE_CONFIG_DIR`; snapshots from another config directory are rejected |
| Antigravity CLI | Last-collected per-bucket quota from documented status-line JSON | Separate snapshot slot and explicit collector binding per authenticated CLI account environment |
| Cursor team | Reported current-cycle per-user spending through the official team Admin API | Exact team member ID plus an environment credential reference; multiple members and separate team keys supported |
| Factory Droid | 5-hour, weekly, and monthly (standard and Core) rate limits plus extra usage balance from Factory's undocumented `/api/billing/limits` | One Factory home per account (`FACTORY_HOME_OVERRIDE`); a user-supplied API key variable, or the opt-in local sign-in |
| Cursor (personal, local sign-ins) | Total, Auto + Composer, and API model usage percentages, included usage, bonus usage, on-demand and team pooled spend, credit grants, and plan name from the DashboardService endpoints Cursor's settings page uses (undocumented) | The Cursor app's sign-in (keychain item `cursor-access-token`, or `cursorAuth/accessToken` in `state.vscdb` read with `sqlite3 -readonly`) |
| Amp | Credit balance and daily Amp Free allowance from the documented `amp usage` command | The CLI's signed-in account, or another account's `AMP_API_KEY` named by an environment variable |
| Devin | Daily and weekly quota from the Windsurf seat-status endpoint the Devin CLI uses (undocumented) | The key from `devin auth login` (local sign-ins) or a named API key variable; only https servers on codeium.com, windsurf.com, or devin.ai |
| omp, Hermes Agent (local sign-ins) | ChatGPT or Claude subscriptions behind logins in omp's `~/.omp/agent/agent.db` (`auth_credentials`, read with `sqlite3 -readonly`; one account per stored row) or Hermes' `~/.hermes/auth.json` | One account per stored login; a Hermes login flagged `relogin_required` shows as signed out |
| Pi, OpenCode (local sign-ins) | The ChatGPT (`wham/usage`, undocumented), Claude (`oauth/usage`), or OpenCode Go (`zen/go/v1/usage`) subscription behind a login those tools store in `auth.json` | One account per stored login; the tools refresh their own tokens |
| Claude Code (live, opt-in) | 5-hour, weekly, and per-model weekly limits (for example Fable) from Claude Code's undocumented `/api/oauth/usage` | The sign-in stored for each bound `CLAUDE_CONFIG_DIR`; falls back to the status-line snapshot |

Claude and Antigravity collectors do not log in, extract tokens, read credential stores, or query undocumented endpoints. Independent snapshot files prevent one slot from overwriting another; labels alone do not establish distinct upstream identity. Authenticate each CLI environment with the intended account and bind the correct collector to it. Switching an upstream login requires reviewing that binding. Live multi-account authentication for these providers has not been verified.

**Personal Cursor subscription quota is not supported.** The team API does not authorize reading unrelated personal subscriptions. Anthropic API billing, Claude Enterprise analytics, Gemini API billing, context-window percentages, and local session token counts are not implemented as subscription quota sources.

## Local sign-ins (opt-in)

**Use local sign-ins** stays off until the user answers the dashboard's first-run question; the answer is stored server-side in `usage-preferences.json` and can be changed in Settings. Turning it off stops all reads of stored sign-ins, including listing the logins Pi, OpenCode, omp, and Hermes hold. When on, it also covers the Cursor app, Devin, those four harnesses, and the Antigravity email (see AGENTS.md). The Claude and Factory readers work as follows:

- **Claude Code:** for each account bound to a config directory, the host first runs `claude auth status` (Claude Code refreshes its own token there), then reads the stored OAuth access token from the macOS keychain item `Claude Code-credentials` (default directory) or `Claude Code-credentials-<first 8 hex of SHA-256 of the directory>`, falling back to `<dir>/.credentials.json`. It calls `https://api.anthropic.com/api/oauth/usage` read-only and shows `five_hour`, `seven_day`, and `limits[]` entries of kind `weekly_scoped` (per-model weekly limits such as Fable). Subset never calls the token endpoint: Anthropic rotates refresh tokens, so refreshing would sign Claude Code out. An expired token asks the user to open Claude Code. If no stored sign-in is found, the status-line snapshot is used.
- **Factory Droid:** reads `<factory home>/.factory/auth.v2.loginkeychain`, `auth.v2.keyring`, or `auth.v2.file`, decrypts it (AES-256-GCM) with the key from the keychain item `Factory CLI` or `auth.v2.key`, and calls `https://api.factory.ai/api/billing/limits` (or the EU host) with the account's organization. When off, a Droid account needs a Factory API key variable; Subset then calls `/api/cli/whoami` for the organization and the same limits endpoint.
- **Configured keys win:** a Factory Droid or Devin account set up with an API key variable always reads that key's account and reports an error when the variable is unset, rather than falling back to the default local sign-in.
- **Harness logins** (Pi, OpenCode, omp, Hermes) are grouped by email and ChatGPT workspace, and join a direct ChatGPT account only when the plans agree, so a Personal and a Team workspace under one email stay separate. Cached reads are keyed by a hash of the stored login, so a replaced login is read again at once.
- **Codex** is unchanged: Codex app-server already reads its own sign-in through a documented interface.

Neither endpoint is documented by its provider, so either can change or stop working. Tokens stay in memory for one request and are never stored, logged, or sent to the view. macOS may show a keychain prompt the first time; choose **Always Allow** so auto-refresh does not wait on it. The approach follows Synara (MIT; `apps/server/src/providerUsage/providers`), Orca, and Zeron, which read the same stores. Subset's implementation is independent and read-only. Keychain lookup is macOS-only; elsewhere only credential files are read.

## Codex banked resets

The resets dialog lists available credits (title, grant and expiry times; opaque credit IDs are dropped) and offers **Use a reset…** with a confirmation step. The host reads the account's credits, chooses the available one that expires first, and calls the documented app-server method `account/rateLimitResetCredit/consume` with that `creditId` and a fresh idempotency key. The dialog names the same credit as "Used next". Outcomes `reset`, `nothingToReset`, `noCredit`, and `alreadyRedeemed` are reported, and status refreshes afterwards. This is the only mutation of provider state in the dashboard.

## Codex account boundary

The first source is Codex usage for ChatGPT-signed-in accounts. The adapter starts one `codex app-server` process per explicitly configured `CODEX_HOME` and calls the documented `account/read` and `account/rateLimits/read` methods. Codex owns login, token refresh, and credential storage. Subset never reads `auth.json`, copies tokens, calls unofficial `wham` endpoints, or accepts API-key billing as ChatGPT subscription usage. Each profile has a local ID and display label; an account signed in with an API key is reported as unsupported. Individual profile failures do not hide successful profiles.

The view shows provider-reported used percentage and reset time per returned limit window. Remaining percentage is labeled as a calculation from reported usage. Codex's response-level `ordinaryUsageAllowed` is preserved separately: explicit `false` means `blocked`, even when quota percentages are positive or reset times have elapsed. Missing permission remains unavailable, never inferred from quota. Per-bucket `rateLimitReachedType` and `spendControlReached` are retained even when a bucket has no windows; the five known reached-limit reasons are allowlisted, and unknown or malformed access fields produce partial data. Aggregate permission and per-bucket restrictions remain distinct. These fields were verified against the generated non-experimental protocol of installed Codex CLI 0.159.3 without reading credentials or account state.

Banked reset count, earliest known expiry, and per-credit details appear only when supplied. Missing observations and partial responses remain visible. Account email and opaque credit IDs are discarded at the adapter boundary. Observation time is captured when app-server returns. The view treats an observation older than five minutes as stale and updates freshness every 30 seconds independently of successful refreshes. Refresh is manual in the package; the standalone host can also refresh on an interval. The text-only fallback likewise includes source, observation time, freshness, calculation qualifiers, access denials, and sanitized failure details.

The read request is local and read-only. `agentUsageResult(status)` yields structured data, a text fallback, and a trusted view ID. The isolated Outright SET-1 integration registers a read-only Codex MCP tool with McpFn and an inspector for this view. Its tool and browser behavior require separate host checks before claiming availability. Account connection is an explicit operation in the standalone local host. Reset redemption is the one provider mutation, behind a confirmation; purchases and other mutations are not exposed.

## Standalone local preview

In the local dashboard, choose **Use current Codex account** to add the existing ChatGPT sign-in, then enter a label and choose **Connect another ChatGPT account**. The host starts the [documented Codex app-server browser login](https://learn.chatgpt.com/docs/app-server) in a new, isolated Codex home. Follow **Continue with ChatGPT** and choose the intended account in the browser. The dashboard polls the login result and adds the account after Codex confirms a ChatGPT sign-in. A browser reload recovers the active sign-in ID, validated link, and state from the same local server, restoring progress and cancellation controls without persisting credentials or login state in browser storage. This recovery does not survive a server restart. Subset never sees or stores OAuth tokens; Codex manages them in its own home. **Remove** unlinks an existing Codex home from the dashboard; for a Subset-managed home it also deletes that local sign-in after explicit confirmation. Cancelling an unfinished login deletes only its newly created home.

The host stores profile labels and Codex home paths in `~/.config/subset/codex-profiles.json` with owner-only file permissions. Managed Codex homes live under `~/.local/share/subset/codex-accounts/`, each with owner-only directory permissions. An owner-controlled profile file may also be supplied directly, for example:

```json
[
  { "id": "personal", "label": "Personal", "codexHome": "/absolute/path/to/personal-codex-home" },
  { "id": "work", "label": "Work", "codexHome": "/absolute/path/to/work-codex-home" }
]
```

Each manually added home must already be signed in with its intended ChatGPT account using Codex. `CODEX_HOME=/absolute/path/to/personal-codex-home codex login` is the Codex-managed login path. `--profile` selects a config overlay within one home and is not account isolation. Do not copy auth files between homes. Account email is not stored in profile metadata or sent to the dashboard status view, so labels should distinguish accounts. A second real ChatGPT sign-in has not yet been available for live two-account verification.

After `npm run build`, use `npm run status --workspace=@subset/usage-web` for structured JSON or `npm run serve --workspace=@subset/usage-web` for the local view at `http://127.0.0.1:4174`. Both run the `@sub-set/usage` CLI from source; see its [README](../usage-cli/README.md) for `subset-usage serve|status|collect`. `SUBSET_USAGE_PROFILES_FILE` selects a different JSON file; the existing `SUBSET_CODEX_PROFILES_FILE` remains a fallback for persisted Codex setups. The default stays `~/.config/subset/codex-profiles.json` and accepts all provider types. `SUBSET_USAGE_DATA_DIR` optionally selects a managed data directory; `SUBSET_USAGE_PORT` changes the loopback port. Stop the server with Ctrl-C or SIGTERM. The server binds only to `127.0.0.1`, checks Host and Origin headers, requires an `X-Subset-Request: 1` header on every API call (which a cross-site page cannot send without a CORS preflight the server never approves), refuses requests the browser marks `Sec-Fetch-Site: cross-site` or `same-site`, and requires a matching browser Origin for account mutations. This is a local preview, not a published CLI/skill, hosted agent view, or public web app. OpenAI documents Codex app-server authentication for local or open-source applications, with a different authorization path required for commercial or hosted services.

### Paid credits and extra usage

Codex paid credits (`rateLimits.credits.balance`) are shown as a credit count, with a dollar estimate at OpenAI's list price of $40 per 1,000 credits. Claude's `extra_usage` (used and monthly limit, in cents) appears as "Extra usage" spending. Factory's extra usage balance and Cursor credit grants appear as balances. Claude plan labels combine the stored subscription type and rate-limit tier, so a Team seat with a `max_5x` tier reads "Team Premium 5x".

### Dashboard view

The shared view (`@subset/usage/view`) shows a summary strip (accounts needing attention, the soonest reset, the highest usage), then one card per account with segmented meters, reset countdowns (exact time on hover), status pills, and inline callouts. The values marked `≈` are calculated; all others are provider-reported. The pace line is a linear estimate from the average rate since the window started and is hidden during the first 5% of a window. Presentation logic lives in `@subset/usage/present` and is unit tested. Clicking a reset time or the banked-reset count opens a resets dialog with the exact reset time, window length and start, time elapsed, used and remaining values, the pace estimate, and banked resets. Card footers show only the last refresh time; the source and age are in its tooltip. `percentMode` switches every value, meter, trend, and the summary between used and remaining. An optional `email` appears under the plan when the provider's local tool reports one (Codex `account/read`, `claude auth status`); it is left out of the agent text fallback. Hosts can pass `toolbar`, `notice`, and `emptyAction` snippets, `header={false}` when they render their own app bar, an `openAccount(id)` callback, and `accountHint(account)` to explain or fix an account that is waiting for data. The standalone host adds an app bar with Usage and Settings pages, an account dialog, and per-account settings with collector setup. Settings hold the percentage display (used or remaining), auto-refresh (off, 5, 15, or 30 minutes; default 5, paused while the tab is hidden), the account list, and clearing usage history. Settings also hold the theme (system, light, dark) and whether trend charts show. Display preferences are stored in browser `localStorage` as per-viewer conveniences. Account names are optional; an unnamed account shows its email, and the default Codex and Claude Code sign-ins carry a **Default** tag. Cards show a status pill in the footer only when something needs attention. Text uses the Twenty One Native typeface from `@21n/fonts@1.0.1`, bundled by the host. Icons are from `phosphor-svelte@3.1.0` (Phosphor). Provider logos come from the CC0 Iconify `logos` set, plus the Factory, Amp, and Pi marks vendored from their own sites in `scripts/logos` (script-free SVGs, regenerated by `scripts/generate-provider-logos.mjs`). Light and dark themes follow the system setting. The first summary card is a 7-day activity heatmap built from local history: one column per day and one row per part of the day (night, morning, afternoon, evening), shaded by the usage added. Hovering or focusing a tile shows the period, points added, and the accounts that used the most. Account names can be edited or cleared from the account settings dialog; when an account has a name, its email moves into the provider and plan line, alongside the logos of other harnesses using it. When one ChatGPT or Claude account is signed in to several harnesses, the host shows one card: the direct account (or the first harness) is read, the stored-login email (read locally) matches the others, and they appear as "Also in" logos; another harness is read only as a fallback when the main read has no usage. ChatGPT accounts are labeled ChatGPT and Claude accounts Claude; "Codex" and "Claude Code" name only the CLIs that read them. The standalone host's footer links to 21n.co and the public GitHub repository; usage.subset.dev is shown as plain text until that site is deployed (`USAGE_SITE_LIVE` in `apps/usage/src/App.svelte`). Accounts without usage windows (such as Amp) always show their balances, even with credits hidden. Harness accounts (Pi, OpenCode, omp, Hermes) carry a `service` naming the subscription they read: the provider filter and the Accounts card's donut chart group them under that service while the card keeps the harness logo. The filter row's options button holds sort order and the trend and credits toggles, which Settings also offers. Accounts that report limit groups side by side show one group per tab: Factory's standard and Core limits, and Antigravity's `<group>-<span>` buckets (Gemini and Third-party), whose span suffix also sets the window length. The Limits summary card lists exhausted windows (0% left) and running-low windows (85% or more used) as separate rows; hovering shows the affected accounts and clicking opens the full list, where each entry scrolls to its card. Accounts can be pinned from the card's options menu (shown under a Pinned filter chip and with a pin in the card footer) and sorted by default order, most recent use (latest rise in local history), or soonest reset; pins and sort order are per-browser conveniences. Trend charts mark resets, detected as sharp drops in recorded usage, with dashed lines.

Trend charts use Apache ECharts (`echarts@6.1.0`, SVG renderer), loaded on demand so the first page load stays small. The standalone host records local history in `usage-history.json` in its data directory (owner-only): only account IDs, window keys, observation times, and used percentages, kept for eight days and thinned when unchanged. Labels, plans, errors, and provider payloads are not stored. A card shows a trend once a window has three observations across at least 30 minutes.

## Claude and Antigravity collectors

In **Manage accounts**, choose **Claude Code quota snapshot** or **Antigravity CLI quota snapshot**, give the account a distinct label, and choose **Add snapshot account**. Expand that account's collector setup and use its generated command, which includes its unique local ID and any custom profile file selection. The command reads JSON on stdin, writes an owner-only quota snapshot, and deliberately produces no stdout.

**Automatic installation.** For a Claude Code account bound to a config directory, or an Antigravity account, **Install collector** (on the card, in account settings, or as a checkbox when adding the account) writes the collector into that CLI's `settings.json`. It is an explicit operation: Subset first copies the file to `settings.json.subset-backup`, keeps every other key, and saves the replaced `statusLine` in an owner-only Subset file. The collector then runs that previous status line with the same input, so an existing display (for example Orca's) keeps rendering. **Uninstall** or removing the account restores the previous `statusLine` unless another tool has since replaced it. Status-line collectors only run in CLI sessions started after installation; a session that was already open keeps its old settings. Account settings report whether the collector is installed, missing, or replaced by another tool. Each collector run records only its time and outcome (`saved`, `no-quota`, or `wrong-directory`) in an owner-only `collector-runs` directory, so the dashboard can say whether the collector has not run yet (for example, a CLI session opened before installation), ran without quota, or ran from the wrong config directory. Settings that are not valid JSON are never rewritten. An account without a config directory cannot be installed automatically.

For manual setup, configure that command as `statusLine.command` in the intended Claude Code account environment or Antigravity CLI's `~/.gemini/antigravity-cli/settings.json`. For example, using the absolute host path and generated account ID:

```json
{
  "statusLine": {
    "type": "command",
    "command": "'/Users/you/.local/share/subset/bin/subset-usage-collect' --account 'claude_example'"
  }
}
```

The default Claude Code account (`CLAUDE_CONFIG_DIR`, or `~/.claude` when unset) appears automatically as **Claude Code (default)** when the documented `claude auth status --json` command reports it signed in. Each refresh runs that command for every Claude account with a config directory to show its sign-in state and plan; Subset strips token variables from its environment, keeps only `loggedIn`, `authMethod`, `subscriptionType`, and `configDirectory`, and skips directories that do not exist because the CLI would create them. Removing the default account is remembered in `usage-preferences.json` next to the profile file; **Use default Claude Code account** adds it back. Quota still comes only from the status-line collector.

For several Claude Code accounts, use one [`CLAUDE_CONFIG_DIR`](https://code.claude.com/docs/en/env-vars) per account (for example `~/.claude` and `~/.claude-work`, launched with `CLAUDE_CONFIG_DIR=~/.claude-work claude`) and enter that directory when adding the account. The host stores it as `claudeConfigDir`, requires it to be unique, and shows the launch command, the `settings.json` path, and the `statusLine` JSON for that account. The collector rejects a payload whose `transcript_path` lies under a different `<config dir>/projects/` tree, falling back to `CLAUDE_CONFIG_DIR` in its environment when no transcript path is present. Claude Code's subprocess env scrub can remove `CLAUDE_CONFIG_DIR`, so a payload with neither signal is accepted. An account without a config directory keeps the unchecked binding. The transcript path is used only for this check and is never stored.

Collectors call a shim, `<data dir>/bin/subset-usage-collect` (default `~/.local/share/subset/bin`), that `subset-usage serve` rewrites on each start to point at the current CLI, so upgrading or moving the install does not break installed status lines. On start, the server also rewrites collectors installed with an older command, but only where the settings still hold the exact recorded collector. When one collector replaces another account's collector in a shared settings file (Antigravity), it inherits the status line that collector had replaced, and `settings.json.subset-backup` keeps the first pre-collector copy. Antigravity keeps one `settings.json`, so only one Antigravity account can collect at a time: installing for a second account is refused while another account's collector is installed there, and that account's settings say which account holds it. Claude snapshots carry no identity, so the host records the email `claude auth status` reports for each account (`claude-identities.json` in the data directory); after a sign-in change, snapshots observed earlier are not shown under the new account. Use the generated command verbatim when paths contain spaces. This collector alone renders no status-line text. To retain an existing status line, use a wrapper that passes the same stdin JSON to the collector and existing renderer, without logging or persisting the raw payload. Subset edits provider settings only through the explicit install and uninstall operations above.

The [Claude Code status-line contract](https://code.claude.com/docs/en/statusline#rate-limit-usage) supplies `rate_limits.five_hour` and `rate_limits.seven_day`, with `used_percentage` and epoch-second `resets_at`. These subscription fields are documented for Pro/Max after the first API response. Claude Code omits a window it has no data for and drops one after it resets, so an absent window is not reported as partial data; a present window with invalid values is. The installed Claude Code CLI uses model-scoped weekly keys such as `seven_day_opus` internally, but they are not documented for the status line. The collector keeps `seven_day_fable`, `seven_day_opus`, `seven_day_sonnet`, and `seven_day_haiku` only if the status-line JSON includes them, shown as for example "Weekly Fable usage". Remaining quota is calculated from reported usage, not inferred from tokens or context size.

The [Antigravity CLI status-line contract](https://antigravity.google/docs/cli/statusline/) supplies `quota.<bucket>.remaining_fraction`, `reset_time`, optional `reset_in_seconds`, and optional `plan_tier`. Remaining quota is reported, while used percentage is calculated. A countdown reset is anchored to the capture time, not the dashboard refresh time.

Snapshots store only allowlisted quota fields and optional plan tier. Emails, transcripts, credentials, workspace paths, and other CLI metadata are discarded. Stored envelopes bind provider and account ID; malformed, cross-account, oversized, or future-dated snapshots are rejected. A startup payload with no usable quota does not overwrite a prior observation. Refresh reloads the last snapshot without changing its capture time; snapshots become stale after five minutes. While a CLI is inactive, the dashboard cannot fetch a new observation. Removing a managed snapshot account deletes its snapshot, not the upstream sign-in; remove the old collector from CLI settings separately.

Use one account-bound collector stream per snapshot slot. Snapshot replacement is atomic, but concurrent collectors for the same slot are last-completion-wins rather than capture-time ordered. Their retained observation timestamp is still shown without modification. Collection rechecks the profile after writing so an overlapping account removal does not leave a recreated managed snapshot.

## Cursor team accounts

Set a team API key in the environment used to launch the local host, for example under `CURSOR_WORK_TEAM_KEY`, then choose **Cursor team spending**. Enter the environment variable name, not the secret, and the exact encoded member ID (`user_...`) from the team's documented `/teams/members` operation. A second member can reference the same team credential variable; another team uses its own variable. Subset stores only references and IDs in owner-only configuration and omits both from dashboard props and profile-list responses. The source is the [official team Admin API](https://cursor.com/docs/account/teams/admin-api).

The adapter calls only the fixed `https://api.cursor.com/teams/spend` endpoint with Basic authentication and bounded pagination/response size/timeouts. It reports on-demand `spendCents`, the included usage value derived from `overallSpendCents - spendCents`, the reported enforced `effectivePerUserLimitDollars` cap, and `subscriptionCycleStart`. An absent cap or cycle end remains unknown; a spending cap is not a personal subscription quota. Authorization failures, missing members, rate limiting, and malformed responses are isolated per account, without exposing credentials or upstream response text.

## Validation and release gaps

Run `npm run test --workspace=@subset/usage` and `npm run test --workspace=@sub-set/usage` after the package build, alongside root `npm run check` and `npm run build`. Root checks build the catalog and usage declarations before checking consuming apps, so they do not require pre-existing ignored `dist` exports. Tests exercise synthetic multi-account provider reads, explicit access denials, safe transport failures, separate snapshot collection, normalization, redaction, profile persistence/removal, pending-login recovery, the local CLI, and host Origin checks. These are not proof of real upstream multi-account login, installed CLI compatibility, or live Cursor API authorization. No public or external-agent availability is claimed by these additions.

## Superfunctions reuse review

Reviewed current `superfunctions-dev` source, public manifests, and README contracts on 2026-09-29, plus npm package versions. `authfn@0.3.0` is for owned session/auth flows; Codex app-server already owns this local account login. `@datafn/client@0.1.1` adds synced persistence that this slice does not need. `plugfn@0.1.0` targets third-party service connections, while this source is a local documented Codex process. `@mcpfn/core@0.0.5` is used by the isolated Outright MCP adapter; the capability itself remains host independent. `@uifn/components-svelte@0.0.1` and React equivalent were evaluated; this view currently needs only semantic HTML and a progress element, so no generic primitive dependency was added. `@superfunctions/observability@0.0.1` was evaluated; the connector avoids logging account data and has no telemetry runtime. **Package/version used in this package: none.** Gaps: hosted agent rendering, live two-account verification, and a release-ready hosted account authorization path remain.

The multi-provider extension additionally reviewed `plugfn/core` implementation, manifest and README, the provider manifest and readiness matrix, and `authfn/core` implementation, manifest and README on 2026-10-01. Published `plugfn@0.1.0` has no supported Cursor provider and requires an auth/database/encrypted persistent connection runtime; `authfn@0.3.0` owns application sessions, not externally issued team API keys or CLI snapshots. Neither is used. The local alternative remains fixed-endpoint read-only collection with environment credential references, not a competing OAuth or connection framework.

The 2026-10-08 UI update checked the current `superfunctions-dev` checkout for icon and chart packages; none is published there, so the view uses `phosphor-svelte@3.1.0` and `echarts@6.1.0` directly as narrow presentation dependencies.

The 2026-10-08 CLI packaging reviewed `clifn/core` (`@clifn/core@0.1.0`, published) and `hostfn`. The CLI has three commands and four flags, so `@clifn/core`'s parser-agnostic runner and output helpers would add a runtime dependency without removing meaningful code; `hostfn` deploys hosted applications and does not cover a loopback-only local tool. Neither is used. The bundle uses `rolldown@1.2.11`, already in the workspace through Vite, as a build-time dependency only. The release workflow is modelled on Superfunctions' `publish-tag.yml` and `resolve-release-tag.mjs`.

This package stays private; `@sub-set/usage` bundles it. Publishing that CLI is a separate, verified release step.
