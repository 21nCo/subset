# M Graph macOS capture (SET-4 and SET-7)

## Foreground recording controls (SET-7)

The menu-bar host now has a separate automatic recording path. On a fresh install its mode is **Off** and its app allowlist is empty. `Allow App…` chooses an installed `.app` bundle and stores its bundle identifier and canonical bundle path; it does not start recording. A different app at another path using the same identifier remains excluded. `Start Recording` or resume enables reads only while that bundle is foreground and Accessibility access is granted. Every newly encountered app stays excluded. `Pause Recording` stops reads without changing the allowlist; `Stop Recording` returns to Off. The `Allowed Apps and Captured Data` submenu has explicit exclusion and per-app deletion actions; an excluded app with retained observations keeps its Delete action. `Delete Captured Data…` removes all captured observations. Either deletion action pauses active recording before erasing data, so the next heartbeat cannot immediately recreate it; Off and Paused remain selected when deleting older data. `Show Last Capture` is an explicit local inspection action. The menu shows the current Accessibility grant, recording mode, and retained observation count. The earlier one-shot `Capture Foreground` and confirmed CLI `capture` operations remain separate SET-4 diagnostic actions and never enable automatic recording.

`CaptureCore/RecordingState.swift` owns the durable allowlist, mode, bounded observation archive, and monotonic throttle; `CaptureCore/ObserverRetryState.swift` owns bounded retry state; `MGraphCapture/RecordingController.swift` owns macOS foreground, sleep/wake, AX notification, permission, and menu-host lifecycle wiring. No web host, product adapter, or model provider consumes the content. The controller observes foreground activation and app-level AX focus notifications, with a two-second heartbeat for value changes and apps that do not emit notifications. It does not synchronously read the remote focused window on the menu thread. AX messaging for notification registration has a 250 ms timeout. Observer creation or any notification registration failure leaves the app eligible for a retry no sooner than two seconds later; a partial registration is removed. After three failures the menu reports that notifications are unavailable and heartbeat checks continue; a successful registration clears the error. App switching, pause, permission loss, and sleep detach the observer, with a fresh attempt when recording is again permitted. It accepts at most one read per three seconds and at most one live request. It cancels and fences in-flight results on app switching, pause, exclusion, deletion, or sleep. Before retaining a result it rechecks the current foreground PID and bundle ID, permission, allowlist, mode, and successful bounded collector outcome. The SET-4 collector already skips secure/password AX roles before reading their text, bounds traversal and output, and fails closed when the focused source changes. Permission revocation also prevents a result from being retained. AX notification coverage varies by app, so the heartbeat is the fallback and capture is not a lossless event stream.

Private files live under `~/Library/Application Support/MGraphCapture`: `recording-settings.json` and `captured-observations.json`. Every new process starts in Off mode even if the previous process was recording; the allowlist remains available for a fresh local Start. The directory is mode 0700; replacement files and a private `recording.lock` are mode 0600. One process holds the OS lock while its recorder is open; another menu-bar instance reports recording unavailable instead of using stale controls. The archive retains at most 50 successful, nonempty, 6,000-character observations and collapses consecutive identical content. A damaged or oversized settings/archive file makes automatic recording unavailable without overwriting the file. All-data deletion can recover a damaged archive, but only after acquiring the same recorder lock; a second live instance cannot erase its owner's archive. Deletion removes the archive file, including its captured text, while retaining the allowlist. There is no cloud synchronization or provider transmission. This is a narrow native staging archive because SET-6 supplies a Node SQLite package but no authorized native IPC service yet; SET-5 conversion and submission to that store are a later host integration, not an asserted SET-7 surface. No catalog surface or release artifact is marked available.

The acceptance host must use the signed bundle launched through LaunchServices on an unlocked macOS desktop. A tagged test invocation uses the launcher's private `recording` directory, which is removed after the owned app exits. Start with that fresh private directory and verify Off, empty allowlist, and no archive before selecting an app. Allow a nonsensitive fixture app, start recording, foreground its unique fixture, and check the archive contains its bundle ID, timestamp, and marker. Keep a second app unselected and verify it contributes no content; test an AX secure text field and verify its value is absent. Trigger repeated notifications and verify the three-second attempt limit and identical-content collapse. Exercise foreground switching, pause/resume, app exclusion, sleep/wake, AX denial and revocation, per-app deletion, and all-data deletion, inspecting both menu state and private files. Restore the original user settings and permission state afterward. The automated Swift tests cover policy, persistence, throttle, and late-result fencing; they do not substitute for this host run. Railway Postgres, Cloudflare Preview, a connected provider sandbox, and Aside Browser have no SET-7 runtime boundary. Signing/notarization, sandboxed AX behavior, and fresh-Mac installation remain separate release evidence.

The focused risk matrix is: default capture/unknown apps (fresh policy and allowlist checks); stale AX work after a control change (generation and deadline checks); rapid allowed-app switches, pause/resume, exclusion, deletion, sleep/wake, and notification storms (one monotonic three-second interval across invalidation, with late-result fencing and deduplication); malformed app selections (selected-app error and no allowlist change); failed AX setup (bounded retry, partial cleanup, and persistent error); denial/sleep (trust and awake checks at dispatch and completion); and damaged storage/deletion (fail-closed load, bounded files, and archive removal). `swift test --package-path native/mgraph`, the Python native checks, `npm run check`, and `npm run build` are the local commands. The native host steps above are still required for final acceptance.

## Prior one-shot capture spike (SET-4)

This is a local macOS development app that reads the foreground application's Accessibility tree when Capture Foreground is selected or a CLI capture is separately confirmed in the app's five-second dialog. The user can start it from Finder or `open MGraphCapture.app`; it appears in the menu bar. `Request Accessibility Access`, `Capture Foreground`, and `Quit M Graph` were the SET-4 menu operations; the recording controls above extend the same host. The one-shot path keeps no history, makes no network requests, and does not include graph inference. The CLI commands `status`, `request-access`, and `capture` are for repeatable native checks. `capture` requires a fresh local approval, pins the foreground process seen before that approval, and writes the result to stdout, so redirect it only to a private temporary file. A launch without approval reports `readFailed` with no text. There is no catalog download or public release.

The native target owns permission checks, foreground app selection, AX traversal, source identity, and the menu. No web host or product adapter consumes it yet. Source identity includes the app name, bundle ID, process ID, window title when exposed, and document URL when exposed. Each JSON result includes an observation time and a state. The collector bounds traversal to 600 queued elements, depth 12, 6,000 output text characters, and a four-second monotonic whole-operation deadline. Child arrays are counted and read by bounded AX ranges; an oversized array fails closed. Text normalization stops at the output budget. AX messaging has a 250 ms per-element timeout. macOS has no bounded read API for every scalar AX string: Chrome static text on this test host returns neither a useful character count nor a ranged string, so that provider reply is length-checked immediately after it arrives. This limits processing and returned text, but cannot cap the provider's allocation before its reply. A separate process with a memory limit would be needed for that stronger guarantee. The menu dispatches traversal to one serial worker queue and stays responsive; its Capture operation stays disabled until a cancelled or completed worker drains. The CLI waits at most four seconds after approval. A late or queued result is discarded. Both paths recheck permission, deadline, and foreground process identity before returning text. The worker requires `AXFocusedWindow` before and after traversal; `AXWindows` order and the app root are not foreground evidence. It compares the focused AX window, title, document, focused element, selected tabs, and web areas across traversal, then checks two subsequent text snapshots and rechecks the focused source after the last text read. Missing focus, changed source metadata, changed text, or failed confirmation returns `readFailed` with no partial text or stale window metadata. The extra reads can cause a volatile page to fail closed or reach the deadline; this spike makes no promise of capturing continuously changing content. Empty accessible trees report `unsupportedApplication`. Secure/password roles and elements whose role or subrole cannot be safely classified are skipped before their text attributes are accessed; other readable elements may still produce a result.


Without `MGRAPH_SIGN_IDENTITY`, `build-app.sh` makes an ad hoc signed local bundle. The source-host check used an Apple Development identity; the destination-host check below uses a Developer ID Application identity. Both use hardened runtime. The bundle contains a declared `AppIcon.icns` for recognition in the Accessibility permission list. `codesign --verify --deep --strict` verifies the signature. `otool -L` and `check-native.py` reject non-system dynamic dependencies; Swift uses the runtime in `/usr/lib/swift`, so no separately installed Swift, Python, or Node runtime is needed to launch the app. Neither bundle is notarized and Gatekeeper rejected both development builds. No app sandbox entitlement is supplied; sandboxed AX behavior remains unverified. This is a viable local development packaging route, not a public download. Notarization, a fresh-Mac launch, and release distribution remain unverified. Apple requires a [Developer ID certificate and hardened runtime for notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

`check-native.py` launches the actual bundle through LaunchServices. This matters because invoking its executable from a terminal can inherit the terminal's Accessibility grant and report a misleading result. The check validates the signature, icon and linked libraries, reads bundled permission state, verifies startup/shutdown, rejects an unapproved CLI capture with zero text, then approves one foreground capture through System Events. Pass `--expect-state available` or `--expect-state permissionRequired` to make a grant or denial assertion; `available` also requires a readable foreground window and nonempty text from that approved capture. A foreground app with no open window correctly fails that strict assertion. `fixture-matrix.py` opens nonsensitive local fixtures in TextEdit, Safari, Chrome, and Firefox; it confirms each CLI capture in that exact owned bundle process, requires a body marker derived from this run's unique fixture title and the matching bundle ID in all four apps, and reports only text length, source identity, and fixture matches. A stale same-app tab or window from an earlier run cannot satisfy that marker. Window-title presence is reported separately because browser AX window-title behavior differs by app. It deliberately does not print captured page text. Before capture or close, both fixture scripts raise a uniquely titled window from the app’s AXWindows list and confirm AXFocusedWindow; browser selection inspects AX descendants for the fixture tab before pressing it and leaves other tab selections alone. The close path sends Command-W only after that check and polls AXWindows plus browser AX descendants for the unique fixture tab's disappearance. Chrome does not expose hidden tabs in AX descendants on this host, so its fixture adapter also uses Chrome's scriptable tab titles to select or close only the uniquely titled tab and verify its absence; the test runner needs Chrome Automation access. A fixture in an older browser tab that cannot be selected safely is reported as a focus or cleanup failure. The scripts delete their private result files. Each LaunchServices check tags its process with an invocation UUID and passes a private shutdown path. The bundle writes its PID to a private ready file and watches the matching shutdown marker for at most 90 seconds, then exits even if the runner was killed or the marker never appeared. The runner validates the kernel executable path and birth time before consent or menu automation. Cleanup writes the marker and waits through one five-second deadline shared with launcher shutdown. It never sends a signal to a discovered bundle PID, so reuse cannot redirect a cleanup signal. A stalled `ps` lookup can use the ready-file identity; an unproven exit fails explicitly. The menu bar title and CLI consent prompt carry the invocation UUID during checks so automation targets the launched instance. The menu check passes its unique TextEdit fixture title to the app; a switched bundle ID or window title produces a zero-text failure alert. Both UI scripts require the runner's unlocked console session, an awake main display, and a readable frontmost application through System Events before opening a fixture. The matrix repeats this check before every app open and capture attempt; a lost desktop stops later fixtures. If the desktop locks after an open, the runner reports the exact app and unique fixture title when it cannot verify closure. Restore the desktop and close only that titled fixture, then rerun the check; a Finder menu-bar count alone does not prove a usable desktop. Foreground activation can race with other desktop automation; a mismatched source identity fails the matrix and should be rerun in a quiet session. `check-menu.py` verifies the real menu click, waits up to five seconds for the asynchronous alert with each read bounded by the remaining time, checks its text and Quit path, and polls until its TextEdit fixture window disappears. It also needs System Events automation access on the test Mac.

To repeat denial and revocation, run `tccutil reset Accessibility dev.subset.mgraph.capture`, then run `native/mgraph/check-native.py --expect-state permissionRequired`. The bundled `status` and `capture` operations must report `permissionRequired`, with no text. Choose `Request Accessibility Access` in the menu bar app and enable this bundle in System Settings > Privacy & Security > Accessibility, then repeat with `--expect-state available`. Reset only this bundle ID; this command removes its existing grant. Turn its System Settings switch off and repeat the denied check to test revocation, then restore the original setting. Each capture checks the current grant, so a revoked grant is reported on the next capture. `request-access` opens the OS permission route but cannot grant permission itself.
