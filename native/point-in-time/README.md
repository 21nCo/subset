# pointInTime (macOS)

pointInTime is a menu-bar app that records which app, window, and website is in front while you work, and rolls that activity into three-minute blocks so you can see where your day went. Activity stays on the Mac unless you choose a classification provider.

This folder holds the capture and storage slice ([SET-19](https://linear.app/21n/issue/SET-19)) and block classification with your own ChatGPT subscription or OpenRouter key ([SET-20](https://linear.app/21n/issue/SET-20)) of the pointInTime outcome ([SET-18](https://linear.app/21n/issue/SET-18)). The timeline and weekly reports (SET-21), the focus ring and companion (SET-22), and the read-only `status --json` agent command (SET-23) are later issues. None of them is implemented here.

## Capability boundary

| Owner | Responsibility |
| --- | --- |
| `Core/` (`PointInTimeCore`) | Activity and segment models, URL redaction, the capture policy (exclusions), the segment recorder state machine, three-minute block rollup, and the SQLite store with migrations and deletion. Classification: the request and response contract (`Classification.swift`), the queue (`ClassificationRunner`), the Codex CLI and OpenRouter providers (`Providers.swift`), the Keychain wrapper, and `Memory.md`. Foundation, Security, and SQLite; no AppKit. Only the providers start a process or open a network connection. |
| `MacApp/` | The menu-bar host: macOS signals (frontmost app, sleep, lock, fast user switching, idle), Accessibility and Apple Events reads, settings, the status menu, the welcome window, and the Classification window and its schedule (every minute, on wake, when the network returns). |

The store is the source of truth. Classification reads blocks from it and writes labels and corrections back. No other app, package, or product imports this code yet.

## What is recorded

While tracking is on and the Mac is awake, unlocked, active, and not idle, the app samples every five seconds:

- **App:** the frontmost app's name and bundle ID, from `NSWorkspace`. No permission needed. Each is capped at 255 bytes of UTF-8 before it is stored (exclusions match the full bundle ID).
- **Window title:** the focused window's title through Accessibility, only while `AXIsProcessTrusted()` is true. Titles are trimmed and capped at 300 characters and at 1,200 bytes of UTF-8. The byte cap is pointInTime's own limit (four bytes for each of 300 characters, so an ordinary title, CJK included, is never shortened), and it stops a title made of a few characters with thousands of combining marks from growing the store. Truncation keeps whole characters only; a title whose first character alone exceeds 1,200 bytes is not stored. Every segment applies these caps (and the app and site caps) itself when it is created, and its text cannot be changed afterwards, so no code path can store a longer value; the store applies them once more as it writes.
- **Site:** for the Chromium browsers Chrome, Brave, Edge, and Arc (the set SET-19 lists), the active tab's URL through Apple Events, only after the user allows Automation for that browser. Only the scheme, host, and path are kept: a host longer than 253 bytes (the DNS limit) drops the URL, and the path is capped at 512 bytes, cut only between whole `%XX` escapes and never inside the escapes of one encoded character, so a shortened path is still a valid path. Query strings, fragments, credentials, and ports are discarded before anything is stored.
- **Private windows in Chromium browsers:** the window title and site are kept only when the browser confirms the window is normal; otherwise only the browser's name is recorded. The reader asks for the front window's id, then addresses that window by id for its `mode`. Nothing about its tabs is requested unless the `mode` is `normal`, so a private window's title and URL are never read. The active tab is then resolved once to its id, and its title and URL are both read from that tab, so neither a window switch nor a tab switch mid-read can pair one title with another URL or with another window's privacy (titles still require Accessibility). Only a `mode` of `normal` confirms; missing Automation, an Apple Event error or timeout, a dictionary without `mode`, or a title with a private-mode marker keep only the app, and the URL is not read after such a title. Apple Events are sent with `NSAppleEventDescriptor`, which is safe off the main thread. The rule lives in `BrowserWindowReport` and `WindowPrivacy` in `Core/` and is unit-tested.
- **Listed Chromium browsers without Automation:** the app name only. Without Apple Events the window's `mode` cannot be confirmed, and the Accessibility title is never used for these browsers.
- **Every other browser:** the app name only, never a window title or URL (an owner decision recorded on SET-19 on 2026-10-17). Without a scriptable window mode a private window could be recognized only by its title, and browsers translate that title into every language they ship (Firefox's German "— Privater Modus", Chrome Canary's "Inkognito"), so a title rule would keep private titles in any language it missed. A browser is any app other than Safari whose Info.plist declares the `http` or `https` URL scheme (read on every sample), plus a built-in list that holds even if the Info.plist cannot be read: the Firefox family (Firefox, Beta, Developer Edition, Nightly, Tor Browser, Mullvad Browser, LibreWolf, Waterfox, Zen, Floorp), Chrome Beta, Dev and Canary, Chromium, Vivaldi, Aside, Edge Beta, Dev and Canary, Opera, Orion, DuckDuckGo, Safari Technology Preview, and others. iPhone and iPad apps are read from the Info.plist at the top of their bundle. An app whose Info.plist cannot be read counts as a browser. Some apps that are not browsers also declare a web scheme (on the development Mac, iTerm and ChatGPT); they are recorded by app name only as well. The rule is `BrowserSupport.forApp` in `Core/`.
- **Safari:** app and window title only, never a URL. Safari's scripting dictionary has no private-window property, so its URLs are not read in this issue (an owner decision recorded on SET-19 on 2026-10-13). A title is dropped when it carries an English private-mode marker (`Private Browsing`, `Incognito`, `InPrivate`) or when it matches Safari's private-window titles in any language Safari ships: the Accessibility title of a private window with a page ("%@, Private Browsing") and of a blank or locked one ("Private Browsing"), read from Safari's string tables with English built in. The title and its private-window evidence are one Accessibility string, so they always describe the same window.
- **Other apps** (apps that do not declare a web scheme): app and window title, never a URL, with the same private-title rule as Safari.

Samples become **segments**: a stretch of unchanged app, title, and site. A change, idle, or any gap closes the open segment. Idle means no input for 120 seconds; the segment ends when the idle period began, or when recording last became possible again if that is later, and anything already stored after that moment (the open segment's last flush, or a segment closed by a title change while you were away) is removed, and the WAL is then checkpointed so the removed titles and URLs do not linger in it. Sleep, display sleep, screen lock, fast user switching, pause, tracking off, and pointInTime's own windows close the segment and record nothing. System sleep and display sleep are tracked separately, because macOS reports them separately and in either order: after the display sleeps, the Mac can wake without it (a dark wake) and stays asleep for pointInTime until the display wakes too, and a duplicate or unmatched wake notification never clears the other. If macOS never posts the display wake, the menu shows Asleep until the display next sleeps and wakes. Recording becomes possible again once none of sleep, lock, a session switch, pause, or tracking off is in effect. This is read from the conditions themselves, so a sleep, lock, or session switch during a write backlog or while the clock is behind (states the menu shows instead) still counts, and idle afterwards keeps what was recorded before it. It also becomes possible again when the clock passes recorded activity (below), so idle never removes rows recorded before the clock was set back. One edge remains: input-free time under 120 seconds recorded just before the clock is set back is not removed later. If samples stop arriving for more than 30 seconds (a suspended process or a clock change), the segment ends at its last confirmed sample instead of claiming the unobserved time. Nothing new may start before the end of activity already recorded, including what earlier launches stored (read from the store before the first sample; if that read fails, the menu shows the store as unavailable and nothing is recorded until it succeeds). While the clock is behind that point, for example after it was set back, the menu says so and nothing is recorded until the clock passes it or Delete All removes it. The app opts out of App Nap while recording, while idle, and during a timed pause, so neither the five-second sample nor the end of a pause is throttled. Titles and URLs are read off the main thread, so a read can finish after the front app changed: every app switch, pointInTime or lock-screen sample, and excluded-app sample ends the open segment and voids reads still in flight, and so does every stop (sleep, lock, a session switch, pause, tracking off, an unreadable store, a write backlog, a clock behind recorded activity, or idle), whether or not a segment is open, and only one read is in flight at a time, across apps, so a slow browser cannot queue up reads; a read that finishes after the front app changed is dropped and the app now in front is read at once. A late read therefore never records across time spent elsewhere.

**Blocks** are fixed three-minute buckets aligned to the Unix epoch. Every UTC offset in use is a multiple of 15 minutes, so buckets also start on local three-minute boundaries, including midnight. A block stores recorded seconds, anonymous excluded seconds, per-app seconds, and the dominant app with the title and site of its longest segment in the block.

**Excluded apps** are never read: no title or Apple Event request is made while they are in front. By default their time is kept as anonymous excluded time with no app name; the menu can switch to recording nothing at all.

## Storage

`~/Library/Application Support/pointInTime/activity.sqlite`. The folder is mode 0700 and the database is mode 0600 (the store refuses to open if it cannot set either mode); SQLite gives its WAL and shared-memory files the same mode. WAL mode, `secure_delete` on, and a `schema_version` table with forward-only migrations. A database written by a newer schema is refused rather than modified, and the menu reports that tracking is unavailable. The version is first read through a read-only connection, before any writable connection exists, so a newer database's WAL is not checkpointed and its journal mode is not changed. A WAL database without a WAL file, as a store closed before its first write is left, is read from its main file alone (SQLite's `immutable` mode), which creates nothing; the one exception is a WAL database whose `-shm` file is missing, for which SQLite may create that index file while the database and its WAL stay unchanged. The migrations then read the version again under the write lock and refuse a newer one, so a version that advanced in between is refused too.

- **Delete Today's Data** removes everything from local midnight until the moment it was asked for, then checkpoints the WAL. A segment that started before midnight keeps its part before midnight. Activity recorded after the request is kept, even when the deletion has to be retried.
- **Delete All Data** removes every segment and block, then checkpoints the WAL and vacuums the file so deleted text no longer remains in the SQLite database or its WAL. This does not guarantee physical erasure from the disk: SSD wear leveling, APFS copy-on-write, and Time Machine or local snapshots can keep older copies. Settings and the excluded-apps list are kept.
- **A deletion counts as done only once its WAL checkpoint completes.** SQLite reports a checkpoint that another connection's read kept from finishing (for example a `sqlite3` shell reading the database) in its result rather than as an error, so pointInTime reads that result. If the WAL could not be fully copied and truncated, the idle retraction, Delete Today, or Delete All stays queued with its error shown and is retried, and the deleted text is gone from both files only after a retry succeeds.
- **Another app using the database delays a write, not pointInTime.** Writes run on the main thread, so none of them waits long for another connection: the checkpoint does not wait for a reader at all, and any other statement waits about 100 ms for another connection's write lock, measured on the clock (SQLite's own timeout adds up requested sleeps, which macOS can stretch several times over). The write then fails, stays queued in order with its error shown, and is retried on the next five-second sample, so while another app holds the database open the menu stays responsive and a deletion shows as pending until it completes.
- Both actions end the open segment first, so it cannot be written back after deletion.
- **Failed writes are retried, in order.** Every store write (a segment save, an idle retraction with its WAL checkpoint, a deletion) goes through `PendingWrites` in `Core/`. A write that fails, for example on a full disk, stays queued with everything after it and is retried on every five-second sample until it succeeds; nothing later runs ahead of it, so a retried save cannot bring back time that a later retraction or deletion removed. Once storage works again, the store holds exactly what applying every queued write in request order would leave. The menu shows the error until the queue drains, so a later successful write cannot hide it. The queue is bounded by one rule, kept in `CaptureSession` in `Core/`: tracking continues only while the queue has room for the next segment save and for the save that closes it, and a save that leaves less room stops capture at once (the menu says the store is not accepting writes) after that closing save, so no recorded segment is ever turned away. While stopped, no capture and no idle retraction is added, so the queue holds at most 256 writes, plus one for each Delete Today requested meanwhile; Delete All replaces it. Retractions and deletions are never dropped or made to delete more to fit. Compaction keeps it small only where it provably stores the same result, using the latest end of everything stored (read from the store before the first sample, read again after a retraction or deletion has been applied, and reset by Delete All) or saved since: while nothing ends after a retraction's end, the retraction drops the queued saves inside its own range, which it would delete anyway, and merges with a queued retraction directly before it into one covering both and the gap between them, which holds nothing. After the clock moves back, rows can end later than the request time, so retractions stay separate and keep the saves before them. Tracking resumes once the queue has room again; time that was input-free before the backlog is still retracted when idle is detected after it, because a backlog alone does not move the idle boundary (a sleep, lock, session switch, pause, or tracking off during it does). Each retry, on a sample or a new write, applies at most 8 queued writes, so recovery from a long outage never stalls the app. The queue lives in memory. Quitting from the menu, and any other termination, including logout and shutdown, first applies every queued write that storage accepts. If some still fail, Quit asks for confirmation and says what would be lost: unsaved activity, a pending deletion or idle retraction, or both. A logout or shutdown loses them without asking.

Settings (tracking, pause, excluded apps, exclusion mode, onboarding) live in the app's user defaults. Tracking is off until the welcome window's **Start Tracking**.

## Classification

Each completed three-minute block is labeled **Focus**, **Neutral**, or **Drift** with a reason of at most 140 characters and a confidence, by the provider you choose in **Classification…** in the menu. The provider is **Off** until you choose one, and nothing is sent while it is off; blocks wait, pending, and are classified once a provider works.

- **ChatGPT subscription (`chatgpt-codex`):** your own `codex` binary, found through your login shell's `PATH` (`$SHELL -l -c`) or a binary you choose (a version manager that is set up only in `.zshrc`, such as nvm, needs the binary chosen). Before each batch, pointInTime runs `codex login status`; if Codex answers "Not logged in", the window says "Sign in with `codex login`", and any other failure is shown with its exit status. **Check Again** looks up the login shell's `PATH` again. It then runs `codex exec --ephemeral --ignore-user-config --ignore-rules --skip-git-repo-check --sandbox read-only --color never --cd <empty folder> --output-schema <file> -o <file> -`, with the prompt on stdin, in an empty folder inside a new mode-0700 temporary folder that is removed afterwards, and stops it after 180 seconds (SIGTERM, then SIGKILL two seconds later; the npm launcher forwards SIGTERM to Codex). The binary's own folder is put first in its `PATH` so a launcher finds `node` beside it. pointInTime never reads Codex's credential files or calls ChatGPT itself. Codex's read-only sandbox still lets its own tools read files on the Mac, and Codex has no stable option to turn them off, so the prompt tells it to answer from the message alone and use no tool; a window title or page crafted to override that instruction is a residual risk of this provider, which **Send window titles** off reduces. Labels record the model as `codex-default`, because the user's Codex config, which could choose another, is not loaded.
- **OpenRouter key (`openrouter`):** chat completions at `openrouter.ai/api/v1/chat/completions` with a strict JSON-schema `response_format` and `provider.require_parameters` (only routes that honor the format), and the model you enter (default `openai/gpt-4.1-mini`; any OpenRouter model that supports structured outputs works). A typed model is used only after Return or leaving the field, so a partial ID is never sent. **Test Key** calls `openrouter.ai/api/v1/key` and sends no activity. The key is kept only in the Keychain, as a generic password with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` that is never synchronized, in the data protection keychain; a local build without the entitlement that keychain needs uses the login keychain, which also stays on this Mac. It is never written to a file, a log, the database, or the app's defaults, and error messages never include it. Requests use an ephemeral `URLSession` with no cache or cookie storage.

**What is sent.** For each completed block: its start time; the name, bundle ID, and seconds of each app used; and for the app used most, its website host and path. The window title of that app is sent only when **Send window titles** is on (it is off by default). Each request also carries the first 8 KB of `Memory.md` and your 20 most recent corrections (the same fields of the corrected block, the previous and new label, and your note). Never sent: excluded apps (a block whose main app is excluded is not sent at all, and excluded apps are removed from every other block's app list), anonymous excluded time, URL query strings (they are never stored), and blocks less than five minutes past their end, which idle detection or the open segment can still change. The Classification window lists these fields.

**The answer is data.** It must be a JSON object with one entry per block id, a label from the three, a non-empty reason of at most 140 characters without control or format characters, and a confidence from 0 to 1. An answer that is not that object or names a block that was not sent changes no label and counts as a provider failure, not against its blocks. A block whose entry is missing, duplicated, or invalid in an otherwise valid answer stays pending and counts one attempt; after five it is `failed`. Failed blocks get a fresh set of attempts after a relaunch, with another provider or model, or with **Retry Failed Blocks**. Reasons are shown as plain text, never as markup, and nothing in an answer is executed.

**`Memory.md`** is your work profile in `~/Library/Application Support/pointInTime/Memory.md` (mode 0600), created from a short template the first time it is read or opened. **Open Memory.md** opens it in your default editor (TextEdit if none is set). Only its first 8 KB, on whole characters, is sent.

**Corrections.** Choose a label for any of today's blocks in the Classification window, with an optional note (up to 280 characters). It is stored (block, previous label, new label, note, time), applied to the block at once, and never replaced by a later model answer, including one already in flight. Corrections are deleted with their block (Delete Today, Delete All, or the block being emptied).

**Queue.** Batches of up to 10 pending blocks, newest first, with one request in flight. A network, rate-limit, process, or unusable-answer failure waits 30 seconds, doubling to at most 30 minutes, or as long as OpenRouter's `Retry-After` asks (up to a day); waking the Mac, the network returning, or a settings change retries at once. A request is built only after the provider is ready (for Codex, after its sign-in check), from the settings in force then: turning the provider off, turning titles off, or excluding an app while it is being set up sends nothing under the old settings. A label is stored only for the block content it judged: each block has a revision that capture bumps when the block's content changes, an answer for an older revision is dropped, and a classified or failed block whose content changes is pending again (a correction is kept). Pending blocks live in the store, so a relaunch resumes them. Each block records its state (`pending`, `classified`, `corrected`, or `failed`), provider, model, and time. A Delete Today or Delete All while a request is in flight discards its answer. The Classification window shows the last success, the last error, and the pending and failed counts.

**Storage.** Schema version 2 adds `label_state`, `label_model`, `label_attempts`, and `revision` to `blocks` (existing blocks start pending) and a `corrections` table. A version 1 database is migrated in place; a newer one is still refused.

## Build and run

The package builds and tests with Command Line Tools alone:

```sh
swift test --package-path native/point-in-time
native/point-in-time/scripts/build-app.sh              # ad hoc signed build/pointInTime.app
POINT_IN_TIME_SIGN_IDENTITY='Developer ID Application: …' native/point-in-time/scripts/build-app.sh
open native/point-in-time/build/pointInTime.app
```

Launch through Finder or `open`, not by running the executable from a terminal: a terminal-launched process inherits the terminal's Accessibility grant and gives a misleading result.

`PointInTime.xcodeproj` is generated by `ProjectGenerator.rb` (xcodeproj 1.27) from the same sources: a static `PointInTimeCore` library, the `pointInTime` app, and the `PointInTimeCoreTests` bundle. Regenerate it after adding or removing a source file; generation is reproducible, and CI fails if the committed project differs. `macos-release.json` opts the app into `scripts/release-macos.mjs` (see [docs/macos-release.md](../../docs/macos-release.md)).

`.github/workflows/point-in-time.yml` runs on macOS for changes here: package tests, the generated-project check, and an unsigned `xcodebuild build test`.

### Permissions

- **Accessibility** (optional): window titles. Request from the welcome window or the menu; grant in System Settings > Privacy & Security > Accessibility. Reset with `tccutil reset Accessibility dev.subset.point-in-time`.
- **Automation** (optional, per browser): sites. The welcome window asks macOS for consent; the app checks permission with `AEDeterminePermissionToAutomateTarget` without prompting before every read, so it never triggers a surprise prompt while you work. Reset with `tccutil reset AppleEvents dev.subset.point-in-time`.
- No App Sandbox: Apple Events to browsers and launching the user's Codex CLI require it to be off. The hardened runtime is on, with only the Apple Events entitlement.

## Superfunctions reuse review

Reviewed `/Users/ar/dev/superfunctions` (branch `next`, commit `9cf3812`) on 2026-10-13.

- **datafn:** the Swift runtime (`datafn/swift`) targets a WebView and Core Data sync topology. pointInTime needs a local-only, single-writer SQLite store with deletion and redaction guarantees and no sync, so it was not used.
- **filefn:** remote file APIs and uploads; nothing is uploaded.
- **plugfn, authfn, billfn:** no accounts or billing. Repeated for SET-20's provider connections on 2026-10-19 (same commit): plugfn's providers are TypeScript connectors (GitHub, Slack, Linear, mail, and similar) with no OpenRouter or model provider, and a Swift app cannot use them. authfn's Swift `AuthFnKeychainCredentialStore` stores an authfn session credential, not an arbitrary secret, and sets no this-device-only accessibility, so pointInTime keeps a small Keychain wrapper of its own. The Codex provider runs the user's own CLI, which no package covers.
- **mcpfn, apifn:** no MCP server or API.
- **uifn, observability:** not applicable to a SwiftUI/AppKit app with no telemetry.

**Package/version used: none.** No Superfunctions code was copied or linked.
