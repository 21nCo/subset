# pointInTime (macOS)

pointInTime is a menu-bar app that records which app, window, and website is in front while you work, and rolls that activity into three-minute blocks so you can see where your day went. Activity stays on the Mac unless you choose a classification provider.

This folder holds the capture and storage slice ([SET-19](https://linear.app/21n/issue/SET-19)), block classification with your own OpenRouter key ([SET-20](https://linear.app/21n/issue/SET-20)), the daily timeline and weekly reports ([SET-21](https://linear.app/21n/issue/SET-21)), the menu-bar focus ring and drift companion ([SET-22](https://linear.app/21n/issue/SET-22)), and the read-only `point-in-time status --json` agent command ([SET-23](https://linear.app/21n/issue/SET-23)) of the pointInTime outcome ([SET-18](https://linear.app/21n/issue/SET-18)). Classification with a ChatGPT subscription through the Codex CLI moved to SET-140. Exports, sharing, write commands, `serve`, and MCP are not implemented.

It links `PointInTimeCore` and AppKit (only to ask whether the app is running) and opens no network connection. |

The store is the source of truth. Classification reads blocks from it and writes labels and corrections back; the reports window and the drift companion only read blocks, and their corrections go through the same `correct` operation. The `point-in-time` command only reads it, through a read-only connection. No other app, package, or product imports this code yet.

## What is recorded

While tracking is on and the Mac is awake, unlocked, active, and not idle, the app samples every five seconds:

- **App:** the frontmost app's name and bundle ID, from `NSWorkspace`. No permission needed. Each is capped at 255 bytes of UTF-8 before it is stored (exclusions match the full bundle ID).
- **Window title:** the focused window's title through Accessibility, only while `AXIsProcessTrusted()` is true. Titles are trimmed and capped at 300 characters and at 1,200 bytes of UTF-8. The byte cap is pointInTime's own limit (four bytes for each of 300 characters, so an ordinary title, CJK included, is never shortened), and it stops a title made of a few characters with thousands of combining marks from growing the store. Truncation keeps whole characters only; a title whose first character alone exceeds 1,200 bytes is not stored. Every segment applies these caps (and the app and site caps) itself when it is created, and its text cannot be changed afterwards, so no code path can store a longer value; the store applies them once more as it writes.
- **Site:** for the Chromium browsers Chrome, Brave, Edge, and Arc (the set SET-19 lists), the active tab's URL through Apple Events, only after the user allows Automation for that browser. Only the scheme, host, and path are kept: a host longer than 253 bytes (the DNS limit) drops the URL, and the path is capped at 512 bytes, cut only between whole `%XX` escapes and never inside the escapes of one encoded character, so a shortened path is still a valid path. Query strings, fragments, credentials, and ports are discarded before anything is stored.
- **Private windows in Chromium browsers:** the window title and site are kept only when the browser confirms the window is normal; otherwise only the browser's name is recorded. The reader asks for the front window's id, then addresses that window by id for its `mode`. Nothing about its tabs is requested unless the `mode` is `normal`, so a private window's title and URL are never read. The active tab is then resolved once to its id, and its title and URL are both read from that tab, so neither a window switch nor a tab switch mid-read can pair one title with another URL or with another window's privacy (titles still require Accessibility). Only a `mode` of `normal` confirms; missing Automation, an Apple Event error or timeout, a dictionary without `mode`, or a title with a private-mode marker keep only the app, and the URL is not read after such a title. Apple Events are sent with `NSAppleEventDescriptor`, which is safe off the main thread. The rule lives in `BrowserWindowReport` and `WindowPrivacy` in `Core/` and is unit-tested.
- **Listed Chromium browsers without Automation:** the app name only. Without Apple Events the window's `mode` cannot be confirmed, and the Accessibility title is never used for these browsers.
- **Every other browser:** the app name only, never a window title or URL (an owner decision recorded on SET-19 on 2026-10-17). Without a scriptable window mode a private window could be recognized only by its title, and browsers translate that title into every language they ship (Firefox's German "— Privater Modus", Chrome Canary's "Inkognito"), so a title rule would keep private titles in any language it missed. A browser is any app other than Safari whose Info.plist declares the `http` or `https` URL scheme (read on every sample), plus a built-in list that holds even if the Info.plist cannot be read: the Firefox family (Firefox, Beta, Developer Edition, Nightly, Tor Browser, Mullvad Browser, LibreWolf, Waterfox, Zen, Floorp), Chrome Beta, Dev and Canary, Chromium, Vivaldi, Aside, Edge Beta, Dev and Canary, Opera, Orion, DuckDuckGo, Safari Technology Preview, and others. iPhone and iPad apps are read from the Info.plist at the top of their bundle. An app whose Info.plist cannot be read counts as a browser. Some apps that are not browsers also declare a web scheme (on the development Mac, iTerm and ChatGPT); they are recorded by app name only as well. The rule is `BrowserSupport.forApp` in `Core/`.
- **Safari:** app and window title only, never a URL. Safari's scripting dictionary has no private-window property, so its URLs are not read in this issue (an owner decision recorded on SET-19 on 2026-10-13). A title is dropped when it carries an English private-mode marker (`Private Browsing`, `Incognito`, `InPrivate`) or when it matches Safari's private-window titles in any language Safari ships: the Accessibility title of a private window with a page ("%@, Private Browsing") and of a blank or locked one ("Private Browsing"), read from Safari's string tables with English built in. The title and its private-window evidence are one Accessibility string, so they always describe the same window.
- **Other apps** (apps that do not declare a web scheme): app and window title, never a URL, with the same private-title rule as Safari.

Samples become **segments**: a stretch of unchanged app, title, and site. A change, idle, or any gap closes the open segment. Idle means no input for 120 seconds; the segment ends when the idle period began, or when recording last became possible again if that is later, and anything already stored after that moment (the open segment's last flush, or a segment closed by a title change while you were away) is removed, and the WAL is then checkpointed so the removed titles and URLs do not linger in it. Sleep, display sleep, screen lock, fast user switching, pause, tracking off, and pointInTime's own windows close the segment and record nothing. System sleep and display sleep are tracked separately, because macOS reports them separately and in either order: after the display sleeps, the Mac can wake without it (a dark wake) and stays asleep for pointInTime until the display wakes too, and a duplicate or unmatched wake notification never clears the other. If macOS never posts the display wake, the menu shows Asleep until the display next sleeps and wakes. Recording becomes possible again once none of sleep, lock, a session switch, pause, or tracking off is in effect. This is read from the conditions themselves, so a sleep, lock, or session switch during a write backlog or while the clock is behind (states the menu shows instead) still counts, and idle afterwards keeps what was recorded before it. It also becomes possible again when the clock passes recorded activity (below), so idle never removes rows recorded before the clock was set back. One edge remains: input-free time under 120 seconds recorded just before the clock is set back is not removed later. If samples stop arriving for more than 30 seconds (a suspended process or a clock change), the segment ends at its last confirmed sample instead of claiming the unobserved time. Nothing new may start before the end of activity already recorded, including what earlier launches stored (read from the store before the first sample; if that read fails, the menu shows the store as unavailable and nothing is recorded until it succeeds). While the clock is behind that point, for example after it was set back, the menu says so and nothing is recorded until the clock passes it or Delete All removes it. The app opts out of App Nap while recording, while idle, and during a timed pause, so neither the five-second sample nor the end of a pause is throttled. Titles and URLs are read off the main thread, so a read can finish after the front app changed: every app switch, pointInTime or lock-screen sample, and excluded-app sample ends the open segment and voids reads still in flight, and so does every stop (sleep, lock, a session switch, pause, tracking off, an unreadable store, a write backlog, a clock behind recorded activity, or idle), whether or not a segment is open, and only one read is in flight at a time, across apps, so a slow browser cannot queue up reads; a read that finishes after the front app changed is dropped and the app now in front is read at once. A late read therefore never records across time spent elsewhere.

**Blocks** are fixed three-minute buckets aligned to the Unix epoch. Every UTC offset in use is a multiple of 15 minutes, so buckets also start on local three-minute boundaries, including midnight. A block stores recorded seconds, anonymous excluded seconds, per-app seconds, and the dominant app with the title and site of its longest segment in the block.

**Excluded apps** are never read: no title or Apple Event request is made while they are in front. By default their time is kept as anonymous excluded time with no app name; the menu can switch to recording nothing at all.

## Storage

`~/Library/Application Support/pointInTime/activity.sqlite`. The folder is mode 0700 and the database is mode 0600 (the store refuses to open if it cannot set either mode); SQLite gives its WAL and shared-memory files the same mode. WAL mode, `secure_delete` on, and a `schema_version` table with forward-only migrations. A database written by a newer schema is refused rather than modified, and the menu reports that tracking is unavailable. The version is first read through a read-only connection, before any writable connection exists, so a newer database's WAL is not checkpointed and its journal mode is not changed. A WAL database without a WAL file, as a store closed before its first write is left, is read from its main file alone (SQLite's `immutable` mode), which creates nothing; the one exception is a WAL database whose `-shm` file is missing, for which SQLite may create that index file while the database and its WAL stay unchanged. The migrations then read the version again under the write lock and refuse a newer one, so a version that advanced in between is refused too.

- **Delete Today's Data** removes everything from local midnight until the moment it was asked for, then checkpoints the WAL. A segment that started before midnight keeps its part before midnight. Activity recorded after the request is kept, even when the deletion has to be retried.
- **Delete All Data** removes every segment and block, then checkpoints the WAL and vacuums the file so deleted text no longer remains in the SQLite database or its WAL. This does not guarantee physical erasure from the disk: SSD wear leveling, APFS copy-on-write, and Time Machine or local snapshots can keep older copies. Settings and the excluded-apps list are kept.
- **A deletion counts as done only once its WAL checkpoint completes.** SQLite reports a checkpoint that another connection's read kept from finishing (for example a `sqlite3` shell reading the database) in its result rather than as an error, so pointInTime reads that result. If the WAL could not be fully copied and truncated, the idle retraction, Delete Today, or Delete All stays queued with its error shown and is retried, and the deleted text is gone from both files only after a retry succeeds.
- **Another app using the database delays a write, not pointInTime.** Writes run on the main thread, so none of them waits long for another connection: the checkpoint does not wait for a reader at all, and any other statement waits about 100 ms for another connection's write lock, measured on the clock (SQLite's own timeout adds up requested sleeps, which macOS can stretch several times over). The write then fails, stays queued in order with its error shown, and is retried on the next five-second sample, so while another app holds the database open the menu stays responsive and a deletion shows as pending until it completes.
- Both actions end the open segment first, so it cannot be written back after deletion.
- **Failed writes are retried, in order.** Every store write (a segment save, an idle retraction with its WAL checkpoint, a deletion) goes through `PendingWrites` in `Core/`. A write that fails, for example on a full disk, stays queued with everything after it and is retried on every five-second sample until it succeeds; nothing later runs ahead of it, so a retried save cannot bring back time that a later retraction or deletion removed. Once storage works again, the store holds exactly what applying every queued write in request order would leave. The menu shows the error until the queue drains, so a later successful write cannot hide it. The queue is bounded by one rule, kept in `CaptureSession` in `Core/`: tracking continues only while the queue has room for the next segment save and for the save that closes it, and a save that leaves less room stops capture at once (the menu says the store is not accepting writes) after that closing save, so no recorded segment is ever turned away. While stopped, no capture and no idle retraction is added, so the queue holds at most 256 writes, plus one for each Delete Today requested meanwhile; Delete All replaces it. Retractions and deletions are never dropped or made to delete more to fit. Compaction keeps it small only where it provably stores the same result, using the latest end of everything stored (read from the store before the first sample, read again after a retraction or deletion has been applied, and reset by Delete All) or saved since: while nothing ends after a retraction's end, the retraction drops the queued saves inside its own range, which it would delete anyway, and merges with a queued retraction directly before it into one covering both and the gap between them, which holds nothing. After the clock moves back, rows can end later than the request time, so retractions stay separate and keep the saves before them. Tracking resumes once the queue has room again; time that was input-free before the backlog is still retracted when idle is detected after it, because a backlog alone does not move the idle boundary (a sleep, lock, session switch, pause, or tracking off during it does). Each retry, on a sample or a new write, applies at most 8 queued writes, so recovery from a long outage never stalls the app. The queue lives in memory. Quitting from the menu, and any other termination, including logout and shutdown, first applies every queued write that storage accepts. If some still fail, Quit asks for confirmation and says what would be lost: unsaved activity, a pending deletion or idle retraction, or both. A logout or shutdown loses them without asking.

Settings (tracking, pause, excluded apps, exclusion mode, onboarding) live in the app's user defaults. Tracking is off until the welcome window's **Start Tracking**.

## Classification

Each completed three-minute block is labeled **Focus**, **Neutral**, or **Drift** with a reason of at most 140 characters and a confidence, by the provider you choose in **Classification…** in the menu. The provider is **Off** until you choose one, and nothing is sent while it is off; blocks wait, pending, and are classified once a provider works. A ChatGPT subscription choice saved by an earlier development build reads as **Off**: nothing is sent, and no other provider is chosen for you.

- **OpenRouter key (`openrouter`):** chat completions at `openrouter.ai/api/v1/chat/completions` with a strict JSON-schema `response_format` and `provider.require_parameters` (only routes that honor the format), and the model you enter (default `openai/gpt-4.1-mini`; any OpenRouter model that supports structured outputs works). A typed model is used only after Return or leaving the field, so a partial ID is never sent. **Test Key** calls `openrouter.ai/api/v1/key` and sends no activity. The key is kept only in the Keychain, as a generic password that is never synchronized. The wrapper asks for the data protection keychain with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, but that keychain needs an entitlement that takes a provisioning profile, which no current build has (Developer ID releases included; see [macOS releases](../../docs/macos-release.md)). Current builds therefore keep the key in this Mac's login keychain (still a never-synchronized generic password asked for as `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`), which does not enforce this-device-only: the key moves with Migration Assistant and keychain backups like any login-keychain item. Enforced this-device-only storage arrives with SET-118; the owner accepted this disclosed fallback for SET-20 on 2026-10-19, and the settings window says the same next to the key field. A key in either keychain is read, saving it in the data protection keychain removes a login-keychain copy, and **Remove Key** deletes both. The key itself is read only when a batch is about to be sent (or for **Test Key** with an empty field); the settings window asks only whether a key is saved, without its data, when it opens and after a save or removal, and the minute timer never touches the Keychain. It is never written to a file, a log, the database, or the app's defaults, and error messages never include it. Requests use an ephemeral `URLSession` with no cache or cookie storage.

**What is sent.** For each completed block: its start time; the name, bundle ID, and seconds of each app used; and for the app used most, its website host and path. The window title of that app is sent only when **Send window titles** is on (it is off by default). Each request also carries the first 8 KB of `Memory.md` and your 20 most recent corrections of settled blocks the request may send (the same fields of the corrected block, the previous and new label, and your note); a block corrected more than once contributes only its latest correction, and corrections of blocks in an excluded app are skipped rather than counted. Never sent: excluded apps (a block whose main app is excluded is not sent at all, and excluded apps are removed from every other block's app list), anonymous excluded time, URL query strings (they are never stored), and blocks less than five minutes past their end, which idle detection or the open segment can still change. The Classification window lists these fields.

**The answer is data.** It must be a JSON object with only a `blocks` list holding one entry per block id with no other properties, a label from the three, a non-empty reason of at most 140 characters without control or format characters, and a confidence from 0 to 1. An answer that is not that object or names a block that was not sent changes no label and counts as a provider failure, not against its blocks. A block whose entry is missing, duplicated, or invalid in an otherwise valid answer stays pending and counts one attempt; after five it is `failed`. Failed blocks get a fresh set of attempts after a relaunch, with another provider or model, or with **Retry Failed Blocks**; when the store cannot be written then (another app holding it, say), the error is shown and the next run tries again. Reasons are shown as plain text, never as markup, and nothing in an answer is executed.

**`Memory.md`** is your work profile in `~/Library/Application Support/pointInTime/Memory.md` (mode 0600), created from a short template the first time it is read or opened. **Open Memory.md** opens it in your default editor (TextEdit if none is set). Only its first 8 KB, on whole characters, is sent. If it cannot be created or read, nothing is sent and the error is shown, rather than sending without your profile.

**Corrections.** Choose a label for any of today's completed blocks in the Classification window, including one that holds only excluded time (it is never sent; its row and those of blocks whose app is excluded say so), with an optional note (up to 280 characters). It is stored (block, previous label, new label, note, time), applied to the block at once, and never replaced by a later model answer, including one already in flight. Corrections are deleted with their block (Delete Today, Delete All, or the block being emptied).

**Queue.** Batches of up to 10 pending blocks, newest first, with one request in flight. A network, rate-limit, process, or unusable-answer failure, or any other error that keeps a batch from being sent or stored (an unreadable `Memory.md`, say), waits 30 seconds, doubling to at most 30 minutes, or as long as OpenRouter's `Retry-After` asks, in seconds or as an HTTP date (up to a day, never negative). Waking the Mac, the network returning after it was unavailable, or a change to the provider, model, key, titles, or excluded apps retries at once, but only a change of provider, model, or key ends a `Retry-After` wait early, and a request still in flight when one of those changes leaves no wait or failure count behind for the new one (its labels are kept); a network interface, VPN, or Wi-Fi change while connected and capture settings such as pause retry nothing. A request is built only after the provider is ready, from the settings in force then: turning the provider off, turning titles off, or excluding an app while it is being set up sends nothing under the old settings. A label is stored only for the block content it judged: each block has a revision that capture bumps when the block's content changes, an answer for an older revision is dropped, and a classified or failed block whose content changes is pending again with its old label, reason, and model cleared (a correction is kept). Pending blocks live in the store, so a relaunch resumes them. Each block records its state (`pending`, `classified`, `corrected`, or `failed`), provider, model, and time. Nothing is sent while a deletion or idle retraction is queued but not applied yet, since the store still holds what it removes. Revisions come from one store-wide counter and are never reused, so an answer does not label a block that a deletion removed or changed while the request was in flight, even one captured again at the same start with the same content; blocks a deletion leaves alone (an idle retraction of later time, say) keep their answer. The Classification window shows the last success, the last error, and the pending and failed counts, which a correction updates at once.

**Storage.** Schema version 2 adds `label_state`, `label_model`, `label_attempts`, and `revision` to `blocks` (existing blocks start pending) a one-row `block_revision` counter, and a `corrections` table. A version 1 database is migrated in place; a newer one is still refused.

## Timeline and reports

**Open Timeline and Reports…** in the menu (⌘T while the menu is open) opens the pointInTime window. A day picker (with ⌘[ and ⌘] for the previous and next day, up to today) chooses the day; the **Week** tab shows that day's week, using the system's first weekday. Opening the window selects today and the current hour; while it stays open, minimized or not, today moves on at midnight, and a day you chose stays chosen. The hourly zoom always shows one of the chosen day's hours: the current one on today, otherwise the hour of the day's first block. Switching to it with a block selected shows that block's hour. Each time the window opens, every minute while it is open, after a classification run, after a correction, and as soon as a deletion or idle retraction removes rows from the store (at once, or on the retry that applies a queued one, even if the checkpoint after it still has to be retried), it reads that week's blocks from the store once and computes every number from them; below each tab it shows the dates covered, when the store was read, and when the latest block in that range ends.

- **Day:** a timeline of the day's three-minute blocks, one named lane each for Focus, Neutral, Drift, Unclassified, and Excluded, zoomed to the full day or to one hour (on a day the clocks change, its 23 or 25 hours by elapsed time; where they change by half an hour, the last hour is cut at midnight, so the zoom never shows the next day). Click a block, use the left and right arrow keys on the focused timeline, or move through the block list with the keyboard to open it in the inspector: its time, label and whether the model or you set it (or, for a pending block classification never sends, such as one of only excluded time or an excluded app, that it is not sent), the model's reason or your note, the provider, model, and confidence, the site and window title of its main app, each app's time, and its recorded and excluded time. A block that has ended can be corrected there with an optional note, through the store's `correct` operation (the same one the Classification window uses), and the timeline and totals update at once. Rings show focus, neutral, and drift as shares of classified time (empty, with a dash, when nothing is classified), with the top apps and sites.
- **Week:** focus-profile cards, per-day bars by category, the half-hour rhythm of focus and drift, a heatmap of focus share for each hour of each day, and a calendar of each day's contiguous stretches by clock time.
- **States:** no activity recorded yet or none on the chosen day, tracking paused, off, or unable to record, classification off (blocks shown unclassified, with a button to the Classification window), a chosen provider that is not set up (no key saved, named as soon as the provider is chosen, asked of the Keychain without reading the key; or a key that cannot be read) or is failing (blocks stay unclassified; the last error and its time, with a button to the Classification window), blocks that could not be classified (with their count and **Retry Failed Blocks**, whose own error is shown if the store cannot be written), and a store that cannot be read (with **Try Again**).
- **Accessibility:** every chart is followed by a plain-text summary, and its marks have VoiceOver labels. A label is never carried by color alone: the timeline names a lane per category, bars carry the category's initial, the rhythm draws focus as a solid line with circles and drift as a dashed line with squares, and the calendar keeps each category in a fixed lane and marks stretches of half an hour or more with its initial. The controls are standard SwiftUI controls, which join the keyboard focus loop, and the window scrolls, with text in system text styles so it can grow; the on-screen checks of these are pending in SET-71.

**How time counts** (`Core/Reports.swift`, the same for every metric):

- A block's label is your correction when there is one, otherwise the model's; pending and failed blocks are **unclassified**. A correction covers the whole block, including its anonymous excluded time, because you know what that time was; a model label covers only the recorded app time it judged, and the block's excluded time stays **excluded**.
- **Idle and other unrecorded time** (paused, off, asleep, locked) is in no total. It is the empty part of a block or a missing block, and a missing block ends a contiguous stretch or run.
- **Focus percentage** is focus over classified time (focus, neutral, and drift); unclassified and excluded time are left out, and a day with nothing classified has no percentage.
- A block belongs to the local day its start falls in. Blocks start on local three-minute marks, so none crosses midnight; activity across midnight counts on each day it covers.

| Metric | Definition |
| --- | --- |
| Day totals | Recorded seconds per category, summed over the day's blocks. |
| Top apps | Each app's recorded seconds. An app excluded when it was captured is recorded without a name, so its time is never named; time recorded before you excluded an app keeps that app's name until you delete it. |
| Top sites | For each block with a site, its main app's seconds go to that site. The store keeps one site per block (that of its main app's longest segment), so site time is approximate to three minutes. |
| Rhythm | 48 half-hours of local clock time. When the clocks go back, the repeated half-hours add into the same slots; when they go forward, the skipped ones stay empty. The week's rhythm sums its days. |
| Weekly bars | Each day's focus, neutral, drift and unclassified time. Excluded time is not plotted; the text summary names it for a day that has any. |
| Heatmap | Seven days by 24 clock hours; a cell's shade is focus over its classified time. |
| Calendar | Consecutive blocks of one category, split at midnight, drawn from their start's clock time to their end's (midnight at the end of the day; on a day the clocks go back, at least to the latest time a stretch passed, a stretch ending as they go back ending at 02:00, so stretches in the two passes through the repeated hour overlap; a stretch across the skipped hour is drawn across it). Times in the repeated hour name their zone ("1:30 AM EDT", "1:30 AM EST") in the calendar, the hourly zoom, the block list and the inspector, and the instant the clocks go back ends the first pass ("2:00 AM EDT"). |
| Typical focus start | The median of each day's focus start (the mean of the middle two for an even count). A day's focus start is the clock time of the first focus run that begins on it; a run continuing past midnight belongs to the evening it began, including one continuing into the week from the day before. The count shown is of days with a focus start; a week whose only focus continued from the week before says so rather than reporting no focus. |
| Start consistency | The standard deviation of those start times, in minutes; shown with at least two days. |
| Longest focus run | The longest stretch of consecutive focus blocks by elapsed time; it continues across midnight within the week. |
| Short drifts | Stretches of consecutive drift blocks starting in the week and holding less than six minutes of drift time. A drift continuing from before the week is never short; one still running when the week ends is judged by its time up to the end of the week. |
| Focus and drift balance | Focus over focus plus drift for the week. |

## Menu-bar ring and drift companion

**The ring.** The menu bar item is a small ring of today's **Focus** (green), **Neutral** (blue), and **Drift** (orange), each arc as long as its share of today's classified time, clockwise from the top over a faint track. It comes from the same day totals as the window's rings (`DayReport` and `CategorySeconds.share(of:)`), so a correction counts the same way, and with nothing classified (a day with no data, or only unclassified or excluded time) the ring is the empty track, never 0%. A mark in its middle shows when tracking is paused, off, or failing. VoiceOver reads the tracking state and the shares, rounded as in the window: "pointInTime is tracking. Focus 62%, Neutral 20%, Drift 18% today." It is redrawn after every classification run, correction, deletion, and tracking-state change, and every minute. The menu shows the tracking state, today's recorded time, today's focus, neutral, and drift with their shares, the provider with its pending and failed counts, and **Open Timeline and Reports…**.

**When a drift is confirmed** (`DriftDetector` in `Core/Drift.swift`):

- The current session is the latest run of blocks with no missing block between them, read through the block holding now (a block starting after it, recorded before the clock was set back, is not part of it), so idle, pause, sleep, or lock for a whole block starts a new session, and it is current only while its last block ended at most one block length ago.
- Each Drift block in it counts; any Focus block resets the count. Neutral, unclassified (pending or failed), and excluded-only blocks neither count nor reset. A block's label is the one reports use: your correction, else the model's.
- A drift is confirmed once the count reaches the threshold: 2 by default, 2 to 5 in settings. It is offered at most once per episode: the first drift block of the episode offered is recorded, and an episode with no reset since that block is the same one, even when it grows, a correction relabels some of its blocks, or an earlier block in its run is labeled drift later (a backlog is classified newest first). A drift is recorded as offered only once it reached you: the panel showed it, or macOS accepted its notification, which is recorded whatever later reads of the store say. A notification is submitted only if, after the permission read and just before submission, a fresh read still offers that drift (the companion and the fallback still on, recording, no focus window, break, or quiet hours, and the same episode); otherwise nothing is sent or recorded. One notification is on its way at a time, and nothing else is offered until macOS answers. A drift that reached you neither way (no panel and the fallback off, no longer offered at submission, notifications turned off in System Settings, or macOS refusing the notification) is offered again at a later refresh while it is still current, and the menu says why the notification was not sent. A new episode needs a Focus block or a new session.
- Quiet hours (off by default; a span such as 22:00 to 07:00 runs past midnight): nothing is offered during them, and a block starting in them resets the count, so an episode never reaches across them.
- Blocks starting before the end of the latest focus window or break are not counted, and nothing is offered until it ends.
- Nothing is offered unless tracking is recording. Labels arrive at least five minutes after a block ends, so a drift is offered then, if the session is still current.

**The companion** is a small panel under the menu bar item. It is a non-activating panel: showing it neither activates pointInTime nor takes keyboard focus from the app in front, and it becomes key only when you click it or move to it with VoiceOver. VoiceOver announces it when it appears; each action is a standard button with a full spoken name, Escape (or **Dismiss**, or its close button) closes it, and nothing is a default button, so Return never acts by accident. It closes itself after 60 seconds. While it is open, the same actions are in the menu bar item's menu, so they can be reached from the keyboard without leaving the app you are in, and no other drift is offered. An action finishes closing the panel (or showing its error) before the companion looks for a drift again, so a drift its own effects make current (a correction ending the run, say) is offered after it, never shown and then closed by it. The actions:

- **Return to Focus** closes it and starts a 25-minute focus window: no drift is offered and no block is counted until it ends. The menu shows the window's end with **End Focus Window**.
- **Take a Break** for 5, 10, or 15 minutes pauses tracking (ending the open segment first, like every control; a longer pause already set, such as one until you resume, is kept) and drift prompts until it ends. A shorter break taken during a longer one keeps the longer end for both, so tracking never resumes while prompts are still held back.
- **Not a Drift** labels each block of the episode **Focus** or **Neutral** through the store's `correct` operation, the one the Classification and reports windows use. Like every correction, it is sent as an example with later classification requests. If a block could not be corrected (deleted meanwhile, say), the other blocks keep their correction and the panel shows the error, opening again when the action came from the menu or a notification; the menu shows it too, and when the panel cannot be shown and the notification fallback is allowed, a notification reports it. Used from an older notification while the panel offers another drift, it leaves that panel open and reports an error by notification.

No action closes tabs, quits apps, or makes a sound, and the companion sends nothing anywhere itself. Settings (**Drift Companion…** in the menu): on or off (on by default), the threshold, quiet hours, and **Send a notification instead**, off by default, for when the panel cannot be shown (the menu bar item is hidden, for example). Turning that on is the only time pointInTime asks macOS for notification permission, for alerts without sound. Whether alerts are allowed is read again before each notification, so turning them off in System Settings takes effect at once, and the notifications are shown as a banner and in Notification Center even while a pointInTime window is in front. The notification offers Return to Focus, a 10-minute break, and Not a Drift as Focus or Neutral. These settings, the focus window and break end times, and the start of the drift last offered are kept in the app's defaults, not in the activity store; the last of these is forgotten once its block is deleted or more than a day old.

## Command-line status for agents

`point-in-time` is a read-only command for scripts and shell-capable agents (Claude Code, Codex, and similar). It prints a day's focus summary from the local store without starting the app, changing any data, or using the network, and works whether the app is running or not.

```text
point-in-time status [--date YYYY-MM-DD] [--json] [--include-titles]
point-in-time --version
```

- `--date` names a day in this Mac's time zone (`TZ` overrides it); the default is today. A day is midnight to midnight, so a day the clocks change is 23 or 25 hours long, and a segment across midnight counts on each day by the three-minute block it falls in.
- `--json` prints one JSON object that follows [`schemas/status-v1.schema.json`](schemas/status-v1.schema.json) (`schemaVersion: 1`); without it the command prints a short text summary.
- `--include-titles` adds window titles and pages (scheme, host, and path) to the output. Without it no window title or URL path appears in either output; app names, bundle IDs, and hosts do. Query strings and fragments are never stored, so they never appear. Excluded apps are never named.

**Installing on PATH.** The app bundles the command at `pointInTime.app/Contents/Helpers/point-in-time`. **Command-Line Tool…** in the menu shows the command to link it and can copy it or reveal the file; you create the link yourself, for example:

```sh
sudo mkdir -p /usr/local/bin
sudo ln -sf /Applications/pointInTime.app/Contents/Helpers/point-in-time /usr/local/bin/point-in-time
```

pointInTime never creates this link, writes to `/usr/local`, or edits shell files. Moving the app breaks the link; create it again. `--version` prints the enclosing app's version and build.

**JSON fields** (schema version 1; every field is always present, `null` when it has no value):

| Field | Meaning |
| --- | --- |
| `schemaVersion`, `command`, `version` | `1`, `"status"`, and the app's version and build (`null` outside an app bundle). |
| `observedAt`, `date`, `timeZone`, `day` | When the store was read; the day as `YYYY-MM-DD`; its IANA time zone; `day.start`, `day.end`, and `day.isToday`. Times are RFC 3339 with the zone's offset. |
| `store` | `state` (`ok`, `missing`, `newerSchema`, `olderSchema`, `locked`, `unreadable`) and the store's `schemaVersion` when it could be read. |
| `freshness` | `lastSegmentEnd` (the latest recorded activity, any day) and `lastClassifiedAt` (when a model last labeled a block). |
| `tracking` | `state` from the app's settings (`notSetUp`, `off`, `paused`, `on`); `pausedUntil` for a timed pause (`null` when paused until resumed); `appRunning`. `on` records only while the app runs and the Mac is in use. |
| `classification` | `provider` (`off` or `openrouter`, never a key) and the day's `pending` and `failed` blocks. |
| `totals` | Whole seconds of `focus`, `neutral`, `drift`, `unclassified` (pending or failed), and `excluded` time, plus `classified` and `recorded`, counted as the reports count them. |
| `focusPercent` | Focus as a rounded percentage of classified time; `null` when nothing is classified. |
| `topApps`, `topHosts` | Up to ten apps (`bundleID`, `name`, `seconds`) and sites (`host`, `seconds`), longest first. |
| `currentDrift` | Today only: the drift companion's current episode (`start`, `end`, `driftBlocks`, `threshold`, and `state`: `belowThreshold`, `companionOff`, `suppressed`, `notYetOffered`, `offered`), or `null`. |
| `titles` | With `--include-titles`, up to ten window titles and pages with their time; otherwise `null`. |
| `errors` | `{code, message}` for each failure; empty on success. |

**Exit codes.** With `--json`, a store failure still prints the object, with `store.state`, `errors`, and `null` totals; text output reports it on standard error.

| Code | Meaning | `errors[].code` |
| --- | --- | --- |
| 0 | Summary printed, including an empty day. | |
| 1 | Internal error: the summary could not be encoded as JSON. Nothing is printed on standard output; the message is on standard error. | |
| 2 | Usage error: unknown command or option, or a `--date` that is not a real `YYYY-MM-DD` date. Nothing is printed on standard output. | |
| 3 | No store: the path does not exist, so pointInTime has not recorded on this Mac. Nothing is created. A store that exists but cannot be reached is exit 6. | `store_missing` |
| 4 | The store was written by a newer pointInTime. It is not changed. | `store_newer_schema` |
| 5 | Another process held the store locked for longer than 500 ms. Try again. | `store_locked` |
| 6 | The store could not be read (a damaged file, permissions on the file or its folder, a sandbox denying access, no Application Support folder), or it predates the schema this command reads; opening pointInTime once updates it. | `store_unreadable`, `store_older_schema` |

**Read-only.** The store is opened with `SQLITE_OPEN_READONLY`, so the command cannot write, checkpoint, or remove the WAL. It reads in one transaction while the app writes through the WAL, opens the WAL index read-only when one exists, and reads a store without a WAL from its main file alone, creating nothing; only a WAL left without its index is read with a writable index, which SQLite may create beside it. The settings come from the app's defaults domain (`dev.subset.point-in-time`), read without writing, and the Keychain is never read.

## Build and run

The package builds and tests with Command Line Tools alone:

```sh
swift test --package-path native/point-in-time
native/point-in-time/scripts/build-app.sh              # ad hoc signed build/pointInTime.app
POINT_IN_TIME_SIGN_IDENTITY='Developer ID Application: …' native/point-in-time/scripts/build-app.sh
open native/point-in-time/build/pointInTime.app
```

Launch through Finder or `open`, not by running the executable from a terminal: a terminal-launched process inherits the terminal's Accessibility grant and gives a misleading result.

`build-app.sh` also builds the `point-in-time` command and places it, signed with the hardened runtime, at `pointInTime.app/Contents/Helpers/point-in-time`; `swift run point-in-time status` runs it from the package.

`PointInTime.xcodeproj` is generated by `ProjectGenerator.rb` (xcodeproj 1.27) from the same sources: a static `PointInTimeCore` library, the `point-in-time` command, the `pointInTime` app, which embeds and signs the command in `Contents/Helpers`, and the `PointInTimeCoreTests` bundle. Regenerate it after adding or removing a source file; generation is reproducible, and CI fails if the committed project differs. `macos-release.json` opts the app into `scripts/release-macos.mjs` (see [docs/macos-release.md](../../docs/macos-release.md)).

`.github/workflows/point-in-time.yml` runs on macOS for changes here: package tests, the generated-project check, and an unsigned `xcodebuild build test`.

### Permissions

- **Accessibility** (optional): window titles. Request from the welcome window or the menu; grant in System Settings > Privacy & Security > Accessibility. Reset with `tccutil reset Accessibility dev.subset.point-in-time`.
- **Automation** (optional, per browser): sites. The welcome window asks macOS for consent; the app checks permission with `AEDeterminePermissionToAutomateTarget` without prompting before every read, so it never triggers a surprise prompt while you work. Reset with `tccutil reset AppleEvents dev.subset.point-in-time`.
- No App Sandbox: Apple Events to browsers require it to be off. The hardened runtime is on, with only the Apple Events entitlement.

## Superfunctions reuse review

Reviewed `/Users/ar/dev/superfunctions` (branch `next`, commit `9cf3812`) on 2026-10-13.

- **datafn:** the Swift runtime (`datafn/swift`) targets a WebView and Core Data sync topology. pointInTime needs a local-only, single-writer SQLite store with deletion and redaction guarantees and no sync, so it was not used.
- **filefn:** remote file APIs and uploads; nothing is uploaded.
- **plugfn, authfn, billfn:** no accounts or billing. Repeated for SET-20's provider connections on 2026-10-19 (same commit): plugfn's providers are TypeScript connectors (GitHub, Slack, Linear, mail, and similar) with no OpenRouter or model provider, and a Swift app cannot use them. authfn's Swift `AuthFnKeychainCredentialStore` stores an authfn session credential, not an arbitrary secret, and sets no this-device-only accessibility, so pointInTime keeps a small Keychain wrapper of its own.
- **mcpfn, apifn:** no MCP server or API. Repeated for SET-23 on 2026-10-22: the `point-in-time` command is a local Swift executable with no server, transport, or published API, and SET-23 excludes MCP, so neither applies.
- **uifn, observability:** not applicable to a SwiftUI/AppKit app with no telemetry.

**Package/version used: none.** No Superfunctions code was copied or linked.
