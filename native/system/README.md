# System (macOS)

System is a menu-bar app that will show where a Mac's CPU, memory, and disk space go, grouped by **origin** rather than as a flat process list: the app a helper belongs to, what launched it, the project a dev server runs in, and the containers inside a Docker-compatible VM. It is a Subset capability in the `planned` state.

This folder holds the app shell ([SET-39](https://linear.app/21n/issue/SET-39)) of the System outcome ([SET-38](https://linear.app/21n/issue/SET-38)), its process sampling ([SET-40](https://linear.app/21n/issue/SET-40)), the origin signals read for each process ([SET-41](https://linear.app/21n/issue/SET-41)), the attribution of processes to origins ([SET-42](https://linear.app/21n/issue/SET-42)), the breakdown of Docker-compatible VMs into containers and compose projects ([SET-43](https://linear.app/21n/issue/SET-43)), the window that shows CPU, memory, and energy by origin ([SET-44](https://linear.app/21n/issue/SET-44)), the disk scanner with its volume summary ([SET-45](https://linear.app/21n/issue/SET-45)), and disk usage by origin with the reclaim rule catalog ([SET-46](https://linear.app/21n/issue/SET-46)): a menu-bar app that shows total CPU, memory pressure, and the three largest origins by memory; a System window that groups processes by app, vendor, launch source, or project and says why each process is in its group; an empty Settings window; a testable `SystemCore` package with the attribution rules, the disk scanner, and the reclaim rules, and a `SystemProcesses` module with the window's view models; a generated Xcode project; and macOS CI. The app does not show disk usage yet (the scanner and the rules have no window until SET-47), run cleanups, call AI providers, or ship the agent helper; those are SET-47 through SET-52.

## Process sampling

`ProcessSource.sample()` reads every visible process once. `LibprocProcessSource` lists PIDs with `proc_listallpids` and reads, per process, `PROC_PIDTBSDINFO` (parent, effective user, start time, name), `proc_pidpath`, and `proc_pid_rusage(RUSAGE_INFO_V6)` (`ri_phys_footprint`, user and system CPU time, `ri_energy_nj`, `ri_billed_energy`). For another user's process, whose `PROC_PIDTBSDINFO` macOS denies, the start time, parent, owner and name come from `kinfo_proc`. The kernel holds a name in a fixed-width buffer (31 bytes in `pbi_name`, 16 in `p_comm`), so the executable's file name is shown instead when the kernel name is empty or a strict prefix of it; any other kernel name is kept. `FixtureProcessSource` replays recorded samples for tests. Command-line arguments are never read, since they can hold secrets; only the executable path is.

- **Identity** is `(pid, startTime)`, so a PID the kernel reuses is a new process. macOS refuses `PROC_PIDTBSDINFO` for another user's process; the identity, parent and owner then come from the process table (`sysctl` `KERN_PROC_PID`), which is readable for every process.
- **Restricted processes.** Without root, `proc_pid_rusage` fails with `EPERM` for other users' processes (about a quarter of them on the development Mac). They stay in the snapshot with `restricted = true` and `nil` usage values, never zero. Any other read failure also leaves the values `nil`, without `restricted`. A process that exits mid-read is left out. The reads are keyed by PID alone, so the start time is read again after them; if the PID changed hands meanwhile, the process is read once more, and left for the next sample if it changes hands again.
- **Units.** CPU times arrive in Mach absolute time units and are converted with `mach_timebase_info` (125/3 ns per tick on Apple silicon). Memory is the physical footprint, the figure Activity Monitor shows as Memory. Energy (`energy`, from `ri_energy_nj`) is the nanojoules the process's own work has used since it started; the System window shows it as Energy. `billedEnergy` (`ri_billed_energy`) is a different figure: nanojoules billed to the process for work other processes did on its behalf, usually far below its own energy, so nothing presents it as the process's energy use.
- **CPU %** is the CPU time delta of one identity over the uptime delta between two samples, with 100% meaning one fully used logical core (Activity Monitor's convention). A process's first sample, including a process that reused a PID, has no CPU value; a process that exited is dropped.
- **Machine CPU**, the figure the menu bar shows, is the busy share of all cores between two samples from `host_statistics(HOST_CPU_LOAD_INFO)` tick deltas, which any user may read, so it includes restricted processes that the per-process figures miss. It is unavailable on the first sample, after a failed tick read, and for the one interval in which a 32-bit counter wraps or resets. The menu bar says CPU is not measured yet only before the second sample and unavailable for any later interval without a figure; while sampling fails, it says unavailable rather than showing the last figure.
- **System memory** (`SystemMemory`): pressure level from `kern.memorystatus_vm_pressure_level` (normal, warning, critical), swap used and total from `vm.swapusage`, physical memory from `hw.memsize`, and app (anonymous minus purgeable), wired, and compressed memory from `host_statistics64(HOST_VM_INFO64)`. A missing or malformed value is `nil`.
- **Cadence.** Every 2 seconds while the main window is visible on screen, every 10 seconds otherwise. A change applies at once, but a sample never starts while another runs or sooner than the new interval after the previous one started. Samples stay in memory; there is no history.

Agreement with Activity Monitor on a real workload is checked in SET-53, not here.

## Origin signals

`OriginSignalReader` (`Core/Signals/`) reads the signals macOS gives a non-root user about where a process came from, once per process identity, and stores them in `ProcessFacts.origin`. SET-42 groups processes from them. Each signal is a value or an `unavailable` reason, and names the interface (`SignalSource`) that supplied it either way. The convenience fields `responsiblePID`, `coalitionID`, `teamID`, `signingID`, `isPlatformBinary`, `launchdLabel`, `workingDirectory`, and `tty` are the bare values (`launchdLabel` only when `launchdMatch` identifies a job, below), `nil` when unavailable or not read yet.

| Signal | Reader and source | Without root |
| --- | --- | --- |
| Responsible process | The private `responsibility_get_pid_responsible_for_pid`, resolved with `dlsym` | Own processes only; others are `denied` |
| Coalition ID | The private `PROC_PIDCOALITIONINFO` flavor (20) of `proc_pidinfo`, resolved with `dlsym`; the resource coalition | Every process |
| Code signature: signing identifier, Team ID and the team's name from the leaf certificate's common name, Apple platform binary | `SecCodeCopyGuestWithAttributes` by PID, then `SecCodeCopySigningInformation`, published once `SecCodeCheckValidity` (without network access) finds the running code matches the file and the kernel's status of the running code (`kSecCodeInfoStatus`) agrees that it is signed, or both are unsigned | Every process; one whose file was replaced since it started (an app updated while it runs, or a signed program replaced by an unsigned file) is `unavailable` |
| launchd jobs: label, plist, domain, `orphaned` | An index of `~/Library/LaunchAgents`, `/Library/LaunchAgents`, `/Library/LaunchDaemons`, and `Contents/Library/LaunchAgents` in each app in `/Applications` and `~/Applications` | Every readable plist; an unreadable plist or an unchecked program is recorded and carried with the jobs found, and a process with no job found then reads `incompleteScan` |
| Working directory | `PROC_PIDVNODEPATHINFO` | Own processes only |
| Controlling terminal | `e_tdev` from `PROC_PIDTBSDINFO`, else from the process table (`sysctl` `KERN_PROC_PID`) | Every process |

- **Private interfaces.** The owner approved the two private interfaces. Each adapter reports `symbolMissing` when its symbol is absent and the call's `errno` (`denied`, `processExited`, or the code) when it fails, so grouping can fall back to the bundle path and parent chain. Neither is linked directly, so a macOS without them still launches.
- **Partial results.** Each reader is independent: a restricted process keeps the signals that succeed (on the development Mac, other users' processes kept their coalition, terminal, and, where the kernel reports an executable path, signature) and records a reason for each that does not.
- **Once per identity and executable.** Results are cached by `(pid, startTime)` and the executable path, and dropped when the process exits. `exec` keeps the PID and start time but replaces the executable (a shell wrapper that runs `exec node server.js`, say), so a process that reappears with another executable path is read again and its signature, launchd jobs, and match follow the new executable. The reads are keyed by PID, so the process is checked afterwards: if the PID changed hands meanwhile, the signals are discarded and recorded as `processExited`; if it now runs another executable, they are discarded and the process stays "not read yet" until the next sample reads its new executable. Reading all of a Mac's processes the first time takes seconds (about 6.7 s for 733 processes on the development Mac, mostly in the Security framework), so one sample reads new identities, oldest first, for at most one second; the rest stay `nil` ("not read yet") until a later sample.
- **Signature cache.** Signatures are cached by executable path, file size, and modification time, plus the status-change time, which the kernel always sets even when an installer preserves an older modification time. The many processes running one executable cost one read, and a rebuilt or updated file is read again. Signatures are read by PID, so a read fills the cache only when it must describe the file as stamped: the process started after the file last changed, the file did not change during the read, and afterwards the PID still belongs to the same process and that process still runs the file (a process that ran `exec` during the read would otherwise file its new executable's signature under the old path). A process started before its file changed may run the replaced version, and one that no longer runs the file when an entry would answer for it is checked first, so either is read directly and neither uses nor fills the entry. The signing information itself comes from the file on disk, so every read is checked against the running code first: a process whose file was replaced (on the development Mac, helpers of an app updated while they ran) reads `unavailable`, not the replacement's identifier and Team ID. An unsigned file cannot be compared with the running code, so it is read as unsigned only when the kernel reports the running code unsigned too; signed code whose file was replaced by an unsigned one, or the converse, reads `unavailable`. Failures are not cached. The cache starts over past 4,096 paths.
- **launchd index.** A job's program is `Program`, which must be an absolute path, else `BundleProgram` (relative to its app bundle), else `ProgramArguments[0]`, which launchd resolves like `execvp` against `/usr/bin:/bin:/usr/sbin:/sbin`. Symlinks are resolved, because the kernel reports a process by its real path (Homebrew services name a symlink). A plist whose program does not exist (`ENOENT`, `ENOTDIR`, `ELOOP`, or not a regular file) is kept as `orphaned`. A program whose path cannot be checked for another reason, such as one under a root-only folder (`EACCES`), is `unchecked`, not orphaned, and is recorded in `scanFailures` with its location and `errno` like an unreadable plist below; for a bare name, only when no `PATH` entry has it and one could not be checked. A plist without a label or program, with a relative `Program`, that does not parse, or that is not a regular file (a folder, FIFO, or device named `.plist`, or a symlink to one; plists are opened without blocking, so a FIFO cannot stall sampling) is listed as unreadable, since launchd cannot load it either. A folder or plist that exists but cannot be read (no read permission, or a plist over 1 MiB, which is not read into memory and is recorded as `EFBIG`; a missing folder is fine) is recorded in `scanFailures` with its `errno`, because launchd, running as root, may still load a job from it: a process whose executable no readable plist names then gets `launchdJobs` `unavailable` with an `incompleteScan` reason naming each failure, not an empty list, and jobs that were found are still returned with the failures in `LaunchdJobs.scanFailures` (the detail view lists them under the jobs). Some Macs have such a plist (the development Mac has a mode 700 root-only one in `/Library/LaunchDaemons`), and there every process without a found job reads as an incomplete scan. Apps are looked for in `/Applications` and `~/Applications` and up to two folder levels below them (`/Applications/Utilities`, a vendor's folder), not inside other bundles and not through symlinked folders. On every sample (about 2.6 ms for 61 jobs on the development Mac), the plists are read again if any plist, plist folder, or application folder appeared, disappeared, changed size, modification time, or status-change time (so a permission fix counts), or could or could no longer be read, and every program is resolved again, so a program that is deleted, created, has its symlink retargeted (as `brew upgrade` does to `/opt/homebrew/opt`), or becomes checkable after a permission fix is followed without a plist change. When the index changes, every process already read looks its executable up again, so a plist added, edited, removed, or made unreadable reaches processes that are already running. Apple's `/System/Library` jobs are not indexed; their programs are platform binaries.
- **launchd match.** A plist names a program, not a process, so `origin.launchdJobs` lists every plist naming the executable and `launchdMatch` says whether they identify the process's own job. It is `job(label:)`, and `launchdLabel` is set, only when the executable is not an Apple platform binary, the parent is launchd (pid 1), every matching plist has the same label, and every plist was read. Otherwise it is `executableOnly` with the first reason that applies: `sharedExecutable` (a platform binary such as `/bin/sh`, `/usr/bin/env`, `/usr/bin/osascript`, or `/usr/bin/sandbox-exec`, which any job or user may run, or a signature that could not be read), `notStartedByLaunchd` (a terminal or app started this copy), `conflictingLabels`, or `incompleteScan` (a plist or program that could not be read may name the executable with another label). So on a Mac with an unreadable plist, such as the development Mac, `launchdLabel` is never set, and SET-42 groups processes from the bundle path and parent chain instead. A process whose parent exited is reparented to launchd too, so `job` is the plists' claim, not launchd's; root-only `launchctl procinfo` would confirm it and is out of scope.
- **Not read:** command-line arguments (they can hold secrets) and root-only sources such as `launchctl procinfo`.

The live tests read the test process's own working directory, terminal state, and code signature, launchd's (pid 1) signature and restricted reads, and record whatever the two private interfaces return. Whether the signals are right for real apps, agents, and dev servers is checked on a working Mac in SET-53.

## Origin attribution

`Attribution` (`Core/Attribution/`) takes one sample's `[ProcessFacts]`, every indexed launchd job (`LaunchdJobIndex.jobs`), a project-marker lookup, and a mount table, and places every process in exactly one group in each of four layers. Each placement (`ProcessAttribution`) names the group, the rule that placed it, a confidence (`rule`, `signal`, or `fallback`), and the evidence used. It reads nothing but the marker lookup and the mount table, so the same inputs always give the same groups. Real-workload agreement is checked in SET-53, not here; misattributions outside the rules below are SET-61 follow-ups.

**App layer.** A closed rule set; the first rule that matches places the process:

| # | Rule | Group | Confidence |
| --- | --- | --- | --- |
| 1 | The executable is inside an outermost `*.app` bundle: a `.app` path component followed by `Contents` (or an iOS app's `Wrapper`), so a folder merely named `x.app` does not count. Helpers, XPC services, login items, and a terminal app's own processes. | The app, by bundle path, shown with the bundle's file name | rule |
| 2 | An Apple platform binary under `/System`, `/usr/libexec`, `/usr/sbin`, `/usr/bin`, or `/sbin`. A signature that is not yet read does not contradict a location on the sealed system volume, which holds only Apple's files. The writable, unsealed locations among them need a platform signature: the volumes under `/System/Volumes` (Data, Preboot, …) and the Data-volume folders that `/usr/share/firmlinks` links in (`/usr/libexec/cups`, and `Caches`, `Assets`, `AssetsV2`, `PreinstalledAssets`, `PreinstalledAssetsV2`, `Speech`, and `CoreServices/CoreTypes.bundle/Contents/Library` under `/System/Library`). A signature that says it is not a platform binary contradicts any location. | macOS, sub-grouped by launchd label when known | rule |
| 3 | A container VM's process, from `ContainerVMRecognizer` (see Container VMs). Its processes run inside the runtime's app bundle or are Apple's Virtualization.framework service under `/System`, so a process it claims is placed here even when rule 1 or 2 also matches. | The runtime: Docker Desktop, OrbStack, or Colima | rule |
| 4 | The process or an ancestor runs a coding agent: `claude`, `codex`, `cursor-agent`, `droid`, `opencode`, `amp`, or `gemini`, as the kernel's process name, the executable's file name, or the agent folder of a versioned install (`…/claude/versions/2.1.304`, the layout of Claude Code's native installer, whose kernel name is the version). The agent's own process counts, so the agent's footprint is in its group. | "Agent: \<name\>", sub-grouped by project | rule |
| 5 | A strict ancestor runs a known terminal app (bundle `Terminal.app`, `iTerm.app`, `Ghostty.app`, `Warp.app`, `WezTerm.app`, `kitty.app`, `Alacritty.app`, `Visual Studio Code.app`, or `Cursor.app`). VS Code and Cursor also start language servers and other tools, so under them only a process with a controlling terminal is in the integrated terminal. | Terminal, sub-grouped by project | rule |
| 6 | The responsible process, else the coalition's earliest-started member (its leader, as far as a non-root reader can tell), is another process inside an app bundle. A responsible PID that belongs to a process started later than this one was reused and is ignored. | That app | signal |
| 7 | `launchdLabel` is set (`LaunchdMatch.job`) and its plist is in an app bundle's `Contents/Library/LaunchAgents` (that app) or the executable has a Team ID (that team). A job with neither falls through, so a Homebrew service reaches rule 8. | The app or team | signal |
| 8 | The executable is under `/opt/homebrew` or `/usr/local/Cellar`. The formula is the folder after `Cellar`, `opt`, or `Caskroom`. | "Homebrew: \<formula\>", or "Homebrew" | rule |
| 9 | The signature has a Team ID. | The team, shown with its name from the signing certificate (`CodeSignature.teamName`, such as "Google LLC") or "Team \<ID\>" | signal |
| 10 | Nothing matched. | The executable path, or the process name without one | fallback |

Later rules that also match are evaluated too (for a container VM, rules 1 and 2 as well), and one that names a different origin than the winner is recorded in `Placement.conflicts` with its evidence; it never changes the placement. The responsible process, the coalition leader, and a launchd job's owning app (rules 6 and 7) name an app, so any other group disagrees with them: a dev server whose responsible process is Terminal stays in Terminal, with Terminal.app recorded. A Team ID (rule 9, or rule 7 for a job outside an app bundle) names who signed the code, so it is recorded when the winner names no signer (macOS, a container VM, an agent, a terminal, or Homebrew), such as a signed tool run in a terminal, and not when the winner is an app bundle, which is that signed code, or an app found through rule 6 or 7. A Homebrew path only restates the executable's location and is never a conflict. A container VM found through its runtime's app bundle is that app: the app named by a responsible process, coalition leader, or launchd job agrees with it, and so does the Team ID of a process inside that bundle.

**Other layers.**

- **Vendor:** Apple (platform binary), the Team ID (named from the certificate when it names the team), unsigned (no Team ID; ad hoc signatures such as Homebrew's included), or signature unavailable. An unread or unreadable signature is never reported as unsigned.
- **Launch source:** the parent's coding agent ("Coding agent: \<name\>"; the agent's own process was started by whatever started the agent), else a terminal session (rule 5's test), else the nearest of the process and its ancestors that has a launchd label (the label), is a login item (`Contents/Library/LoginItems` inside an app), is inside an app bundle or has an app as its responsible process ("Launched by an app"), or has launchd as its parent ("System"). A chain that ends at a parent missing from the sample is "System" with `fallback` confidence and the missing PID as evidence. On a Mac with an unreadable launchd plist (see Origin signals) no process has a label, so launch agents show as System or as launched by an app.
- **Project:** the nearest folder at or above the working directory holding `.git`, `package.json`, `Cargo.toml`, `go.mod`, `pyproject.toml`, `Package.swift`, `Gemfile`, or `pom.xml` (looked for in that order, with `lstat`, once per folder per call, `/` included), else the working directory itself (`/` too), else no project when the working directory is unavailable. Markers are looked for only on local volumes: the mount table is read once per call with `getmntinfo_r_np(MNT_NOWAIT)`, which asks no file system and fills a buffer owned by that call (plain `getmntinfo` shares one buffer across the process, so concurrent calls could overwrite or free it), and the walk stops at the first folder on a volume without `MNT_LOCAL` (SMB, NFS, AFP, most FUSE volumes), whose `lstat` can hang. Such a process's project is its working directory, with the skipped volume as evidence. The working directory is readable only for the user's own processes.

**Totals.** Each group and subgroup sums its members: memory (`physFootprint`, marked `isApproximate` because shared pages count once per member), CPU percent, and energy, which is the billed energy (`ri_billed_energy`) as SET-42 specifies. Billed energy covers work other processes did on the members' behalf and is usually far below their own use (see Units), so the members' own energy (`ri_energy_nj`) is summed separately as `ownEnergy`. Each figure counts measured and unmeasured members, and `restrictedCount` counts restricted members separately; a member without a value is never added as zero, and a group with no measured member has no sum. Sums saturate rather than overflow.

**Identity and cost.** A group's `OriginGroupID` is built from paths, labels, Team IDs, and names, never PIDs, so it is the same in every sample and the UI can keep expansion and selection. Groups are ordered by identity and members keep the order they were given. A parent index is built once per call and each ancestor question (nearest agent, nearest terminal, inherited launch source) is answered for the whole sample at once, so attribution is linear in the number of processes; the 2,000-process test checks the step count on a 2,000-deep chain, where a walk per process would follow about two million links.

**Known limits** (SET-53 checks real workloads; SET-61 collects follow-ups):

- Rule 2 precedes rules 4 and 5, so `/usr/bin` tools started from a terminal or agent (`/usr/bin/login`, `/usr/bin/git`, `/usr/bin/python3`) are macOS, and Apple binaries outside the rule's locations, such as `/bin/zsh` outside any terminal or agent, are unattributed.
- A platform binary never gets a launchd label from SET-41's signals (`LaunchdMatch.sharedExecutable`, and Apple's own jobs are not indexed), so the macOS group has no label subgroups yet.
- The coalition leader is the earliest-started member in the sample; macOS does not tell a non-root reader which member leads.
- Rule 1 takes the outermost `*.app` wherever it is, so a process run from an app bundle nested in a framework or Homebrew keg (framework Python's `Python.framework/…/Resources/Python.app`) joins that app's group, even a dev server in a terminal or agent session.
- Terminal and agent subgroups use the process's own project; a process whose working directory cannot be read (another user's) is in the group but in no subgroup.
- Working directories inside app bundles and app containers (an XPC service's bundle folder, `~/Library/Containers/…/Data`) become projects of their own under the "working directory itself" rule.
- A working directory on a network or FUSE volume, or in a local volume mounted inside one, never finds a marker on that volume, so a repository on a network share is grouped by its working directory rather than its root.
- The live marker lookup stats files in each working directory's folders. The app attributes every sample (SET-44), so for a process working in a folder macOS protects (Documents, Desktop, Downloads), macOS may ask the user to let System access that folder; if the user declines, no marker is found there and the process's project is its working directory. Whether and when that prompt appears on a real Mac is checked in SET-53.

The fixture tests record one process per rule (Chrome renderer helpers, an XPC service and login item, an Apple daemon and an unsigned binary on a writable system volume, a container VM through a stand-in recognizer and through `ContainerVMRecognizer` (ContainerVMTests), `node` under `claude` under `zsh` under Ghostty, a dev server in Terminal and in VS Code's integrated terminal, an app found through its responsible process and coalition, a launch agent with an orphaned plist of the same label, a Homebrew service and its workers, a signed tool, an unsigned binary), the precedence between conflicting signals and which of them are recorded as conflicts, the project walk through `/` and its stop at a network volume, totals with restricted members, group identity across two samples, and the linear-time bound. A live test attributes this Mac's processes and checks that each is placed once per layer.

## Container VMs

When Docker Desktop, OrbStack, or Colima runs, its processes form one origin group (App rule 3) with what macOS measures for them, and beneath it the containers and compose projects the runtime's own CLI reports from inside the VM. The two figures are shown side by side and never reconciled: the VM reserves memory that its containers may not use, and the containers' figures come from the Linux kernel inside the VM.

**Recognizing the VM** (`ContainerVMRecognizer`, `Core/Containers/`). A closed rule set over one sample; the first that applies places a process:

| # | Rule | Runtime |
| --- | --- | --- |
| 1 | The executable is inside an outermost `Docker.app` or `OrbStack.app` bundle and is not a client (below): the UI, backend, helpers, and Docker Desktop's bundled QEMU or hypervisor | Docker Desktop, OrbStack |
| 2 | Lima's host agent for a Colima instance, a `limactl` whose PID Lima recorded in that instance's `ha.pid` in Colima's Lima home (`_lima/<instance>/ha.pid` in `~/.colima` or `~/.config/colima`), in a file written after the process started, or Colima's daemon, `colima` whose parent is launchd (`brew services`, `colima daemon`), by file name or kernel name. A host agent no Colima instance records, such as plain Lima's (`limactl start`, which keeps its instances in `~/.lima`), is left alone, and so is a recorded PID a later process reuses | Colima |
| 3 | A process outside any app bundle with an ancestor placed by rule 1 or 2: what the runtime started, such as `qemu-system-*`, `ssh` port forwarders, and `socket_vmnet` under Lima's host agent. It stops at a shell (`zsh`, `bash`, `sh`, `dash`, `fish`, `tcsh`, `csh`, `ksh`, `nu`), a coding agent, or a client in between, so neither that process nor what runs in it (Docker Desktop's terminal, a coding agent started there) is the VM. It also stops at another app's bundle: what that app starts is the app's | That ancestor's |
| 4 | Apple's Virtualization.framework VM service (`com.apple.Virtualization.VirtualMachine`), which launchd starts for a runtime: the runtime of its responsible process, else the one runtime among the other members of its coalition (Colima started in Terminal has Terminal as the VM's responsible process, in a coalition shared with Lima's host agent) | That process's |

Only the VM and daemon side counts, so only it creates a group and starts a poll. A client is not the VM: the `docker` CLI (`Docker.app/Contents/Resources/bin/docker` is what `/usr/local/bin/docker` usually links to, and OrbStack's `xbin/docker` what `~/.orbstack/bin/docker` links to), `docker-*` credential helpers and anything in a `cli-plugins` folder, `kubectl`, `hub-tool`, `com.docker.cli`, and OrbStack's `orb` and `orbctl`. Neither is a `limactl` or `colima` command run from a shell, or by such a command (`colima start` and the `limactl` it runs, `limactl list`); a `limactl` that Colima's daemon or the host agent runs is Colima's by rule 3. These, including System's own `docker` child, are placed by the other App rules: a client inside an app bundle stays with that app (rule 1), and a command run in a terminal with that terminal session.

A responsible PID that belongs to a process started later than the VM service was reused and is ignored. A coalition holding two runtimes leaves the VM service unrecognized, and it stays in macOS. So does a coalition with more VM services than its runtime runs: one for Docker Desktop or OrbStack, and one per Lima host agent that does not run QEMU for Colima, so a tart or vfkit VM started in the same terminal as Colima is not counted as Colima's. `ContainerVMRecognizer.groups(in:)` gives each running runtime's members and totals (`GroupTotals`) without the rest of attribution, so the app needs no project-marker lookups to show them.

**Asking the runtime** (`DockerCLI`). Only a `docker` executable at one of these paths, tried in order, is run: `/usr/local/bin/docker`, `/opt/homebrew/bin/docker`, `~/.orbstack/bin/docker`, `/Applications/Docker.app/Contents/Resources/bin/docker`; never one found through `PATH`. It runs without a shell, with only `HOME` and a fixed `PATH` in its environment, so `DOCKER_HOST`, `DOCKER_CONTEXT`, and `DOCKER_CONFIG` cannot redirect it. Before it runs, the current context is read the way the CLI reads it: `currentContext` in `~/.docker/config.json`, whose endpoint is in `~/.docker/contexts/meta/<sha256 of the name>/meta.json`; no context, `default`, or an empty `config.json` is `unix:///var/run/docker.sock`. An endpoint that is not a `unix://` socket (`ssh://`, `tcp://`) is a remote context and the CLI is not run. The socket's real path names the runtime (`~/.docker/run/docker.sock`, or `docker-cli.sock` or `docker.raw.sock` in `~/Library/Containers/com.docker.docker/Data/` that it links to, Docker Desktop; `~/.orbstack/run/docker.sock` OrbStack; `docker.sock` in a profile folder under `~/.colima` or `~/.config/colima` Colima), and only that runtime's group shows the breakdown; another running runtime says which one the context reaches. A socket that names no runtime (Podman's, one forwarded from another machine, a custom path, or a Colima profile under a custom `COLIMA_HOME`) is not asked at all, and every running runtime says the context is not recognized, even when only one runs: its containers may be in no recognized VM.

It then runs `docker --host unix://<real path> ps --format '{{json .}}'` and `docker --host unix://<real path> stats --no-stream --format '{{json .}}'`, with the real path of the socket that named the runtime, not the path the context gives. Pinning the real path keeps both commands on the socket that was checked, even if the current context changes during the poll or a runtime repoints a shared link such as `/var/run/docker.sock` (Docker Desktop and OrbStack each do when they start), so one runtime's listing is never joined with another's usage or shown under it; the report names that endpoint (the breakdown's tooltip shows it). A socket that does not exist is not asked, and is checked before ownership: the links its path starts are followed to the path the last one names (Docker Desktop's `/var/run/docker.sock` still points at `~/.docker/run/docker.sock` while its engine is stopped and that socket is gone), the runtime that path names says its daemon is not running, and when it names none, every running runtime says so, not that the context is unrecognized. Each has a 5-second timeout, past which the command is stopped (`SIGTERM`, then `SIGKILL` a second later) and the report says so at once. Output is read as it arrives and capped at 8 MiB.

**Cadence.** `ContainerPoller` runs the two commands at most once every 10 seconds, only while the main window is visible and a runtime's VM is running, and never twice at once. With only the menu bar in use it never runs. Hiding the main window cancels a poll in progress: the running command is stopped the same way and no further one starts. It also drops the last report, so a reopened window shows "not measured yet" until the next poll, and every breakdown or reason shown carries the time it was observed. The poll runs beside the sampling loop and never delays a sample. The breakdown, in the detail pane of the VM's App group, is at most 96 points tall (about five lines) and scrolls past that, so every project and container stays reachable however many run, and the rest of the pane keeps its space. Quitting the app cancels a poll and sends its running command `SIGKILL` at once (`CommandRegistry.shared.shutDown()`), since the delayed one would never fire. The launch and the kill share a lock, so the shutdown finds each command either not launched, and keeps it from launching, or launched with a known process ID it kills itself before it returns, without waiting for the thread that launched it; no command starts after that.

**Reading the output** (`DockerOutput`, `ContainerBreakdown`). Each line is one JSON object. `docker ps` gives the ID, the first name, the image, and the `com.docker.compose.project` label from `Labels` (a compose project name never holds a comma, so splitting the labels on commas is safe); `docker stats` gives `CPUPerc` (percent of one virtual core, so it can pass 100) and `MemUsage` (`used / limit`). Sizes use the CLI's binary units (`B`, `KiB`, `MiB`, `GiB`, `TiB`, `PiB`) or decimal ones (`kB`, `MB`, `GB`, `TB`, `PB`). The two lists are joined by ID (one may be a prefix of the other), never by name. Two rows with different IDs are different containers even when they share a name (one recreated between the commands). A container in only one of the lists is kept, without usage or without labels. Containers are sub-grouped by compose project, with standalone containers after. The CLI's `--` placeholder is unmeasured, not zero. A line that is not a JSON object with an `ID` is skipped and counted (`skippedLines`), and a value that is not a number with a known unit, or a `MemUsage` that is not a string of exactly `used / limit`, is left `nil` and counted (`unreadableValues`; an absent `MemUsage` or `-- / --` is unmeasured); the view shows both counts.

**No breakdown.** The VM group stays without containers and shows the reason when no CLI is at a candidate path, the context cannot be read or is remote, the daemon is not running (the CLI's "Cannot connect to the Docker daemon", or "failed to connect to the docker API" from Docker CLI 28 and later), a command times out, fails with another exit status (its first error line is shown), cannot be started, prints more than the cap, or prints lines none of which can be read. Empty output is a running daemon with no containers.

**Known limits** (a real runtime is checked in SET-53): a Colima home under a custom `COLIMA_HOME` or `LIMA_HOME` is not read, so its host agent and VM are not shown as Colima; Kubernetes, Podman, remote contexts, and starting, stopping, or pruning containers are out of scope; whether the VM service's responsible process and coalition are as described for each runtime is verified on a real Mac in SET-53. Without a process's arguments, the coalition fallback matches VM services to host agents by count, not by which VM each one runs: if Colima's own VM service is in another coalition, another tool's VM in the host agent's coalition is counted as Colima's. The client names, the `ha.pid` layout, and the launchd-parent rule for `colima` are also checked against each runtime's real layout in SET-53, and so is the process layout of Docker Desktop's and OrbStack's terminals, which rule 3 leaves out at the shell. So are the socket paths that name each runtime; a context on any other socket gets no breakdown.

The tests use recorded `docker ps` and `docker stats` lines (parsing, compose grouping, units, malformed lines), a stub `docker` script (success, the endpoint pinned across a context change, the environment it runs with, timeout, a stopped daemon in both CLI wordings, another failure, unreadable output, a missing or non-executable binary, a remote context, a local socket no runtime owns (Podman's) with one runtime running, a socket that does not exist, a default link that dangles toward Docker Desktop's socket or no default socket at all, an empty config, a shared link repointed to another runtime between the commands, runaway output, the stub's process gone after a timeout, the cap, a cancellation, or the quit-time kill, including one that ignores `SIGTERM` and needs `SIGKILL` and a quit while the command is launching (no command starts after it), the 10-second limit, the menu-bar-only rule, hiding the window during a slow `docker ps`, and overlapping polls), and process fixtures for Docker Desktop, OrbStack, Colima with `vz`, with QEMU, and under `brew services`, plain Lima beside and without Colima, a stale or reused `ha.pid`, the `ha.pid` files read from a Colima home, another app and what it starts under a runtime, the clients and transient commands that are not the VM, a shell and coding agent run under Docker Desktop and OrbStack, coalitions with more VM services than Colima runs, and the VMs the recognizer must leave alone (UTM, QEMU run by hand, Podman).

## System window

`SystemMonitor` attributes each successful sample off the main actor (`Attribution` with the live project-marker lookup, mount table, and container VM recognizer, and the origin reader's own launchd index for orphaned plists) and hands the result to `ProcessesWindowModel` (`SystemProcesses`), which the window and its tests share.

- **Layers and rows.** A segmented picker switches between App, Vendor, Launch source, and Project (⌘1–⌘4, from the View menu while the window is key). Each group row shows its name, process count, restricted count, and summed CPU, memory, and energy; it expands to its subgroups (a launchd label under macOS, a project under an agent or the terminal) and processes. Expansion and selection are kept by group identity, so a new sample keeps them while the group exists. Each layer remembers its own selection and restores it while its group still exists; a selected process stays selected in every layer and its group opens; a selected process that exits leaves its subgroup or group selected.
- **Sorting and filtering.** Sort by CPU, memory, or energy, largest first, from the picker or the column titles; a missing value sorts last, then by name. ⌘F focuses the name filter: a group whose name matches is shown whole, and a group with a matching member opens to show only the matches (and can be closed again).
- **Figures.** Group memory is shown with "≈", since shared pages count once per member, and a footnote says so. CPU is percent of one core. Energy is the members' own energy used since each started (`ownEnergy`), not a rate; the detail pane also shows the billed energy SET-42 sums as the group's energy. A restricted process shows "Restricted" for every figure, its group a separate restricted count, and no sum counts it as zero; a group with no measured member shows "–" and sorts last.
- **Detail pane.** For a process: its group in the current layer, the rule, a confidence badge (Rule, Signal, or Fallback, with what each means), each piece of evidence in plain language ("Inside `Google Chrome.app`", "Child of claude (pid 4120) in ~/dev/subset"), conflicting rules, executable path, PID and parent, Team ID, launchd label, restricted state, and figures, with the raw origin signals below. For a group: its totals and restricted count, the path it stands for (an app bundle, login item's app, or project folder), and for a container VM's group the containers inside it.
- **Header.** Memory pressure, used of physical memory, app and compressed memory, swap, total CPU and logical cores, process and restricted counts, the time the sample was observed, and the sampling state: waiting, sampling every 2 or 10 seconds, stale once no sample has arrived for three intervals (the Mac slept, or sampling stalled), or failed with the reason. Stale and failed figures stay on screen, labeled as from the last sample.
- **Menu bar.** Below CPU and memory pressure, the App layer's three largest groups by memory; choosing one opens the window on it (switching to the App layer and clearing a filter that hides it). Groups without a measured memory sum are never listed as zero.
- **Row actions.** Reveal in Finder and Copy path, from a row's context menu or the detail pane, for a process's executable or a group's app bundle or folder. By owner decision there is no Quit or Force Quit in v0.
- **Keyboard and accessibility.** Up and Down move through rows, Right expands a group, Left collapses it or selects the row's group, ⌘1–⌘4 switch layers, ⌘F filters. Each row is one accessibility element whose label names it and its state and whose value reads its figures, saying "about" for approximate memory and how many members are not measured; each control has a label and value.

The view-model tests (`Tests/ProcessesTests`, run by `swift test` and as the `SystemProcessesTests` bundle by `xcodebuild test`) build samples through the real `Sampler`, `OriginSignalReader`, and `Attribution` from recorded processes (Chrome and its helpers, Ghostty, `claude` and `node` in a project, Apple daemons, restricted processes) and check layer switching and selection, sorting, filtering, restricted counts, the footnote, the stale and failed states, the detail text, keyboard expansion, the menu bar's top groups, and that every row in every layer, fully expanded, has a non-empty accessibility label and value. Grouping correctness on real workloads is checked in SET-53; on-screen, VoiceOver, and full keyboard review in SET-58.

## Disk scanning

`DiskScanner` (`Core/Disk/`) scans one folder or local volume; the default scope is the user's home folder. Each worker reads a folder with `getattrlistbulk` in batches of up to 128 KiB, asking for the name, type, modification time, Finder flags (for the bundle bit), file flags, inode, date added, link count, logical and allocated size, and, through `FSOPT_ATTR_CMN_EXTENDED`, the APFS private size, real device, clone ID, and extended flags. A file that shares blocks with a clone is also opened, never read, to map its blocks with `F_LOG2PHYS_EXT`. A pool of worker threads (4 by default, `DiskScanner(workers:)`) shares one queue of folders. It needs no Full Disk Access: what it may not read is counted as unknown and listed.

- **Sizes.** Each item has a logical size (`st_size` over all forks), an allocated size (blocks on the volume: a sparse or compressed file allocates less), and a private size, the space freed if only that item were deleted. Totals use allocated sizes. The private size is a lower bound: APFS counts blocks a clone shares or a local snapshot keeps as not private (a file older than the latest snapshot frees nothing), it reports a compressed file's data, kept in an extended attribute, as not private, and a folder never counts the blocks its clones share as freed, since a clone outside the scan may hold them.
- **Hard links.** A file with several links counts once, at its link with the smallest path; the others are flagged `countedElsewhere`. One link frees nothing, so a hard-linked file shows a private size of zero, and its private bytes count in the closest folder holding every link. A folder reached twice (a directory hard link on HFS+) is read once and its own allocation counts once; the other entry counts zero and is flagged `countedElsewhere`.
- **Clones.** APFS reports a clone ID and a shared byte count (allocated minus private) but not which blocks are shared, and a clone changed after cloning gets a new ID while still sharing most blocks with the first (a clone of it gets yet another), so totals do not rely on IDs. For a file with `EF_MAY_SHARE_BLOCKS` and shared bytes, the worker opens it (`O_NOFOLLOW`, never read, checked to be the same inode) and maps its data with `F_LOG2PHYS_EXT` into physical ranges on the container, rounded to the volume's block size, skipping holes. Each folder, package, and root counts the union of the ranges of every such file beneath it, so a file, its pure clones, a changed clone, and clones of that count each block once, as do clones split across folders and packages and a hard-linked clone; the file itself still shows its own allocated and private sizes. When the ranges cannot be read (the file cannot be opened, has more than 4,096 ranges, or its ranges do not add up to its allocated size, as with a compressed file or a resource fork), the file falls back to its clone ID: it adds its private bytes and its shared bytes count once per clone ID in each folder, which is exact only for one group of pure clones (`EF_SHARES_ALL_BLOCKS`). Such a file, if it shares only some blocks, and every folder, package, or root whose total includes shared bytes from two or more sources (clone IDs, or a clone ID and read ranges) is flagged `allocatedUpperBound`, since it may count blocks more than once, as `du` does; an unflagged total is exact.
- **Boundaries.** A symbolic link counts as itself and is never followed (folders are opened with `O_NOFOLLOW_ANY`, so a link swapped in during the scan is not followed either). Mount points and automount triggers (`DIR_MNTSTATUS_MNTPOINT`, `DIR_MNTSTATUS_TRIGGER`) count as zero and are not crossed. Firmlinks are followed, so scanning `/` reaches `/Users` and `/Applications` on the data volume, while `/System/Volumes/Data`, a mount point, is not read a second time. A network or other non-local volume is refused (`notLocal`). The chosen root may be a symbolic link; its real path is scanned. The root is read with `getattrlist` (`FSOPT_NOFOLLOW`) and classified like any entry: its own allocation counts (exFAT and FAT give every folder one), a chosen package is one item, and a chosen placeholder folder is not read. A chosen volume is scanned although its root is a mount point. Mount status is read when a folder's parent is listed, so each folder is checked again once opened: its file system ID (`fstatfs`, which matches `ATTR_CMNEXT_REALDEVID`; `st_dev` gives the startup disk's system volume the data volume's) and inode must be those its entry reported. A folder on another volume, mounted there after its parent was listed, becomes a mount point and is not read; a folder that another took the place of on the same volume is not read and is flagged `incomplete`. This holds for folders, folders inside packages, and the root. A firmlink is not checked: its entry describes the link on the read-only system volume, not the folder it opens.
- **Packages.** A folder with the bundle bit, or whose name has an extension and that Launch Services calls a package (`.app`, `.photoslibrary`, `.xcodeproj`, not `.framework`), is one item whose sizes are its own allocation plus its contents' totals; the contents are read but not listed, and Launch Services is not asked about folders inside a package. That holds when the package itself is the chosen root.
- **iCloud placeholders.** A dataless file (`SF_DATALESS`) counts as zero allocated and private, keeps its logical size, and is flagged `dataless`; a dataless folder is not read. A package whose contents include either is flagged `containsDataless`, since its contents are not listed. Every scan thread, including the one that resolves and classifies the chosen root before the workers start, sets `IOPOL_MATERIALIZE_DATALESS_FILES_OFF`, so the scan never downloads anything; nothing is read on the caller's thread.
- **Unreadable items.** A folder or package that cannot be opened or read (permissions, a privacy-protected folder or library without Full Disk Access), the chosen root included, or an entry whose attributes fail (its kind is `other` when no type came back with the error) has an unknown size (`sizes == nil`) and is listed in `unreadablePaths`; every folder above it is flagged `incomplete`, meaning its sizes are a lower bound. A folder inside a readable package that cannot be read is listed too, and leaves the package sized but `incomplete`.
- **Progress and cancellation.** `onProgress` receives the items read, allocated bytes so far (folders' own allocation included, hard links and folders reached twice once; clones are resolved only in the final totals, so each copy counts in full), and the folder most recently started, at most once per `progressInterval` (100 ms by default), one call at a time, with the item count always rising. Cancelling the scan's task stops each worker before its next batch and before its next `F_LOG2PHYS_EXT` call, retries included (a call interrupted 8 times in a row is not retried again), so a clone whose mapping was cut short falls back to its clone ID and its flag, and returns the tree read so far, with outcome `cancelled` and unread folders flagged `partial`.
- **Result.** A compact tree in memory only: one fixed-size record per item, children contiguous, names in one buffer. Package contents are not items. Nothing is written to disk.
- **Times.** Each item keeps `touched`, the later of its modification time and its date added (`ATTR_CMN_ADDEDTIME`, when it was created in or moved into its folder), so a download that keeps its server's modification time, or a project folder moved into place, counts from when it arrived. A folder's own time changes when an entry in it is added, removed, or renamed, not when a file deeper down is written. The reclaim rules' age tests use it.

`VolumeSummary.read(volumeOf:)` reports the volume's capacity, available for important use (`volumeAvailableCapacityForImportantUsage`), plain available (`volumeAvailableCapacity`), purgeable as the difference (unavailable when either is missing or the first is smaller), and the number of local Time Machine snapshots from `tmutil listlocalsnapshots` run on the scanned volume's mount point (`/` for the startup disk), without a shell and with a 5-second timeout. A `Snapshots for …:` heading (`Snapshots for disk /:`, or `Snapshots for volume group containing disk /:`) is skipped. Their sizes are always reported as unavailable. A failure, a timeout, or a line that is not a snapshot name makes the count unavailable with the reason, never zero; an empty list is zero.

The tests (`DiskScannerTests`, `DiskEntryTests`, `VolumeSummaryTests`) build fixtures in a temporary folder on the runner's APFS volume: a sparse file, a hard link pair and a link outside its folder, a file and two `clonefile` copies in two folders, a clone written to after cloning beside a folder of pure clones, a clone of that changed clone moved beside the first clone group (two clone IDs sharing nearly every block), a sparse file whose clone is written in its data and inside a hole, a changed clone split between a folder and a package, and a hard link to a changed clone, each of whose totals must equal, unflagged, the space its construction uses (the original's allocated size plus the changed clone's private size, checked against an independent `F_LOG2PHYS_EXT` block count), and a changed clone with mode 000, whose ranges cannot be read, so it and every total above it are flagged and at least that space, while a folder of pure clones beside it stays exact, symbolic links to a folder and file outside the root, a `.app` package beside a `.d` folder and the package scanned as the root, a folder with mode 000, a `.app` with mode 000 as a child and as the root, a readable `.app` with a mode-000 folder inside, a tree whose totals must equal the sum of `lstat` `st_blocks` and `st_size` (each inode once) and `du -sk`, and a 50,000-file tree cancelled at its first measured bytes, which must return within 500 ms with partial totals, and a changed clone whose first range lookup cancels the scan, which must make no further lookup, return within 500 ms, and count the clone, flagged, from its clone ID. With one worker, a listed folder replaced by another holding new files, and an exFAT image mounted on a listed folder, after the root's batch is reported, are not read; the startup disk's root folders must pass the identity check, firmlinks excepted, and a counting Launch Services stand-in must not be asked about the `.lproj`, `.framework`, `.appex` and `.app` folders inside a package, and must see `IOPOL_MATERIALIZE_DATALESS_FILES_OFF` on the thread that asks about the chosen root and about each entry. ## Disk by origin and reclaim rules

Both work on a finished scan's tree and read nothing else but what is listed here; the results stay in memory. Neither deletes, moves, or runs anything: cleanup is SET-48, after confirmation. Results on a real home folder are checked in SET-54, not here.

**Disk by origin** (`DiskOrigins`). Every entry directly inside `~/Library/Application Support`, `Caches`, `Containers`, `Group Containers`, `Preferences`, `Logs`, and `HTTPStorages` is matched to an installed app, then to a vendor by the app's Team ID, with SET-42's `Origin` types (`Origin.app(bundlePath:)` or `Origin.macOS`; `Origin.apple`, `.vendor(teamID:)`, `.unsigned`, or `.signatureUnavailable`). The identifier is the entry's name without `.plist` (Preferences) or `.binarycookies` (HTTPStorages), and in Group Containers without a Team ID prefix (`ABCDE12345.`) and a `group.` or `groups.` prefix. The first rule that applies places the entry (`DiskOriginRule`):

| # | Rule | Placed as |
| --- | --- | --- |
| 1 | The entry is a folder a developer tool's reclaim rule names (`Caches/Homebrew`, `Caches/Yarn`, `Caches/pip`) | That developer tool |
| 2 | In Group Containers, an app group an installed app's signature declares (`com.apple.security.application-groups` or its restricted variant), whatever its name: Shortcuts declares `group.is.workflow.my.app`, which holds the user's shortcuts. A container named for a declared group with the declaring app's Team ID before it (`TEAMID.group.com.example`) is that app's too; another team's prefix is not. Declared by several apps, only their vendor when they share one, and not attributed when they do not | The app, the vendor, or not attributed |
| 3 | An identifier that is an installed app's bundle ID or extends one by whole components, without case (`com.example.app.helper`, `COM.EXAMPLE.APP`), the first app by path when two copies share it (two Xcode versions). This comes before every rule below, so an installed app's data is never a leftover, even when its signature could not be read | The app |
| 4 | An Apple identifier (`com.apple.…`) no installed app has: macOS's own data, never a leftover | macOS with vendor Apple |
| 5 | A group container with a Team ID: an app of that team whose bundle ID is or extends the identifier, or the other way round; else the one app that team signs; else, with several, their vendor only | The app or the vendor |
| 6 | In Group Containers, the one app whose bundle ID extends the identifier by whole components (`group.com.example` for `com.example.app`) | The app |
| 7 | The name of exactly one installed app (its file name, `CFBundleName`, or `CFBundleDisplayName`, without case), even one shaped like a bundle ID | The app |
| 8 | Any other bundle ID (three or more dot-separated components of letters, digits, `-`, `_`, the first all lowercase letters), or a group container's Team ID no installed app has. Only when every app in the app folders was read (`InstalledApps.isComplete`), and in Group Containers every installed app's signature and entitlements too (`InstalledApps.signingComplete`), since an app that could not be read may own it; otherwise a possible leftover (`possibleLeftover`), not attributed, which makes the leftovers unknown: the App leftovers match is incomplete, or unavailable with none found, with a reason naming what was not read (`unread`, `unreadSigning`), and the leftovers group is a lower bound, present even when empty | A leftover, risk `review` |
| 9 | Nothing matched (`Google`, `DiagnosticReports`, a container named by a UUID) | Not attributed |

`DiskOrigins.report` sums the entries by app (with macOS), by vendor (named from the signing certificate, "Team \<ID\>" without one), leftovers, and not attributed, (possible leftovers among them), and the reclaim matches' items by their rule's developer tool (Xcode, Node.js, npm, pnpm, Yarn, Homebrew, Cargo, Gradle, pip; Docker's image space is inside its VM and is not summed). Each group gives summed allocated and private sizes and says when they are lower bounds: an item's size is unknown or a lower bound; for a developer tool, one of its matches is incomplete or unavailable (DerivedData could not be read); for the entry groups, a Library folder was not listed in full or holds an entry whose name did not come back (`unlistedFolders`, the same check App caches and App leftovers use), since any app may have had entries there. Items are distinct entries; a hard-linked file's blocks count once, in the link the scan counts them in, so an item whose blocks another link counts adds none to the allocated sum and makes it a lower bound; blocks two items' clones share count in each item's allocated sum, never in the private sum. A group with an item flagged `allocatedUpperBound`, or with two or more items that may hold clones (a file flagged `sharesBlocks`, a folder listing one, or a package whose private size is below its allocated size), sets `allocatedUpperBound`: its allocated sum may count clones' blocks more than once. The tree does not say which blocks two items share, so this is conservative; one item holding every clone stays exact. Matches and groups sum with the same helper (`DiskTree.sum`).

**Installed apps** (`InstalledApps`). Tests inject the list. `InstalledApps.read()` lists `/Applications`, `~/Applications`, and `/System/Applications`, and their subfolders one level down (`Utilities`, a vendor's folder), reading each app's `Contents/Info.plist` (a regular file of at most 1 MiB, not followed if the file itself is a link) for its bundle ID and names, or for an iPhone or iPad app on Apple silicon its wrapped bundle's (`Wrapper/<name>.app/Info.plist`), which is also the bundle whose signature is read. An entry named like an app that is not a folder or a link to one (a file, an alias, a link to nothing), or a folder with neither `Contents` nor a wrapped app, is not an app and is skipped. A folder that cannot be listed (one that does not exist is empty) and an app whose bundle ID cannot be read are recorded in `unread`, which makes the list incomplete (`isComplete` false): any entry could then be that app's, so no entry is a leftover. The login items and helper apps inside an app (`Contents/Library/LoginItems`, `Contents/Helpers`) are listed under their own bundle IDs and belong to it. Each app's Team ID and certificate name come from its static signature, checked against its certificate chain without hashing its files or using the network (`kSecCSBasicValidateOnly`), since the Team ID only groups data; an invalid or unreadable signature is unavailable, never unsigned. The app groups come from the same signature's entitlements; each login item and helper declares its own. On the development Mac, reading its 228 apps took about 1.2 seconds.

**Reclaim rules** (`ReclaimRules`, `catalogVersion` 1; `ReclaimRules.all` and the `ReclaimRuleID`, `ReclaimRisk`, `ReclaimCleanup`, and `ReclaimYield` values are what SET-52's schema exports). Exactly these rules; other candidates are SET-61 follow-ups. Each rule has a name, its location, a risk, a cleanup kind, a yield (how much of what it measures its cleanup frees, and when: all of it at once for `npm cache clean --force` and `yarn cache clean`; all of it moved to the Trash, freed only once the Trash is emptied, for every Trash cleanup; part of it for `pnpm store prune` and `brew cleanup`; an estimate for `xcrun simctl delete unavailable`; Docker's reported upper bound; or nothing for the Trash), an explanation of what the data is, and a note on how it is rebuilt. `ReclaimMatcher.matches` gives each rule's matches in catalog order:

- **Bytes.** A match reports the private size summed over its items, at least what deleting them all frees, and the allocated sum beside it (`ReclaimBytes.scanned`). That is the items' usage, not a yield. What running the cleanup frees at least, at once (`ReclaimMatch.freedAtLeast`), is that private sum only for a command that deletes every item (`ReclaimYield.deletesAllMeasured`: the npm and Yarn caches). A Trash cleanup (`movesAllMeasuredToTrash`: every rule whose cleanup is Trash, Trash per item, or Trash per app) frees nothing at once, since trashed items use the same volume until the Trash is emptied, which System never does; `ReclaimMatch.movedToTrash` gives the private sum it moves there, which emptying the Trash afterwards frees at least. No yield is guaranteed for the pnpm store and the Homebrew cache, whose commands keep referenced packages and current downloads, for unavailable simulators (an estimate, below), for Docker, or for the Trash. An item whose size is unknown, or a lower bound (`unreadable`, `partial`, `incomplete`), makes the sums incomplete. An item whose allocated size may count blocks clones share more than once (`allocatedUpperBound`), or two or more items that may hold clones of each other, as for the By origin groups, set `allocatedUpperBound` on the match, since its allocated sum may then be more than the items use; the private sum is unaffected.
- **Coverage.** Every folder a rule searches (its rule folder and the DeviceSupport, Archives date, Downloads, and home folders it walks) must have been listed in full, and so must the folders above a rule folder that was not found, since only then is it absent; a rule folder that was found is judged by its own listing. One that was not (unreadable, cancelled, replaced before it was read, another volume, an iCloud placeholder that was not downloaded, a folder the scan read at another path through a directory hard link, a link, which the scan does not follow, in place of the folder or of any folder above it, such as a `~/Library/Developer` moved to another disk) makes the match incomplete, and so does an entry in a searched folder that could not be read and whose type or name did not come back, since it may be a folder, an installer, or a `package.json` (`DiskTree.searched`, one classifier for every rule), and a rule's own folder that is not a folder, and so do candidates that could not be judged (a device whose `device.plist` cannot be read, an installer or project whose time is unknown); with nothing found, the match has unavailable bytes and no items with the reason, so the window says the answer is unknown rather than none. App caches and App leftovers need their Library folders listed in full the same way, and the By origin groups are lower bounds when one was not (a linked `~/Library/Caches` included); a regular file in place of a folder holds nothing, so the rules below it are absent. A cache an app that could not be read may own (a possible leftover in `~/Library/Caches`) makes App caches incomplete.
- **Items and roots.** Each item has the folder of its rule that holds it (DerivedData, a DeviceSupport folder, a project folder, a Library folder, Downloads), which SET-48 never removes, and the item's tree index, sizes, flags, and time. A rule whose folders the tree does not hold, under folders listed in full, has no match, and so does one with no items and nothing it could not search. Rules work for any scan that holds their folders: a scan of `/` or of the home folder holds them all; a scan of a folder inside the home folder (outside `~/Library` and hidden folders) is searched for stale `node_modules`.
- **Stale `node_modules`.** A project's age is the latest `touched` of the project folder and everything in it outside `node_modules` folders, so a file written deep in `src` keeps it fresh. A package's contents are not items, but the scan keeps the latest `touched` of the entries read inside each package, which counts too, since a file saved inside an `.xcodeproj` leaves the package's own time alone. A project with an item whose time is unknown, that was not listed in full by the shared coverage rule (another volume inside it included), or with a package something inside of which could not be read or is not downloaded, is not stale and makes the match incomplete. The search starts at the home folder, found the same way (a scan of `/` that could not list `/Users` gives an unavailable match), or at a scanned root inside it outside `~/Library`, hidden, and `node_modules` folders. Hidden folders are skipped because they hold installed tools, not projects (`~/.vscode/extensions`, `~/.nvm`, `~/.cursor`), and so is `~/Library` (apps' bundled packages); a project in a hidden folder is never suggested.
- **Simulators.** The installed runtimes (`SimulatorRuntimes.read`) are the runtime disk images in `/Library/Developer/CoreSimulator/Images/images.plist` (`runtimeInfo.bundleIdentifier`) and the `.simruntime` bundles in `/Library/Developer/CoreSimulator/Profiles/Runtimes` and in the runtime volumes mounted under `/Library/Developer/CoreSimulator/Volumes`, read without running `simctl`. No list and no bundles is no runtime; an `images.plist`, a runtimes or volumes folder, or a runtime bundle's `Info.plist` that exists but cannot be read or parsed (or names no runtime) leaves the list unknown and the match's bytes unavailable, as does an `images.plist` runtime without a bundle identifier, so no device is called unavailable from a missing answer. Runtimes registered as `standaloneBundles` in `images.plist` are read the same way. A downloaded runtime in `/Library/Developer/CoreSimulator/Cryptex/Images/bundle` (`SimRuntimeBundle-<UUID>`) that no image naming a runtime in `images.plist` comes from (`sourceParentUUID`, `sourceParentBundleMountURL`) also leaves the list unknown, since it may be registered where System does not read (a MobileAsset). A device whose `device.plist` cannot be read, names no runtime, is missing, or was listed by the scan as not downloaded or unreadable (then it is not opened), or whose folder was not listed in full, is not counted and makes the sum incomplete. This plist, the runtime list, and installed apps' `Info.plist` files, folders, and signatures are read with the thread's policy set not to download iCloud placeholders (restored after), and a placeholder plist (`SF_DATALESS`) is unreadable, so no read downloads a file. `xcrun simctl delete unavailable` decides for itself which devices it deletes, so this figure is an estimate (`ReclaimYield.estimated`), with no guaranteed yield.
- **Docker.** `DockerCLI.imageUsage()` runs `docker system df --format json` the way the container poll runs its commands (see Container VMs: a fixed candidate path, the current context checked and the socket's real path pinned with `--host`, no shell, a fixed environment), with a 30-second timeout because it sizes every image, container, and volume, and reads the `Images` row's `Size` and `Reclaimable` (`2.064GB (61%)`). Docker rounds to four significant digits, so the reclaimable figure is read as the most it may be: the printed value plus half a unit in its last digit (`2.064GB` is at most 2,064,500,000 bytes, `1GB` 1,500,000,000; bytes are exact). The match keeps that figure as an upper bound only (`ReclaimBytes.dockerReclaimable(upTo:)`, `upperBound`; `bytes` is `nil`), since it counts every image no container uses and `docker image prune -f` removes only dangling ones. A missing CLI, a remote or unrecognized context, a stopped daemon, a failure, or output without a readable `Images` row is unavailable with the reason. The matcher never runs it; the caller passes its result in, and without one there is no Docker match.

**Known limits** (SET-54 checks a real home folder; SET-61 collects follow-ups): apps outside the listed folders (in `~/Downloads`, on another volume) count as not installed, so their data shows as leftovers, which is why leftovers are `review`; an app's helper that keeps data under an unrelated bundle ID (`com.google.Keystone` for Chrome) is a leftover too; a container named by a UUID (newer macOS) is not attributed, since naming its app means reading its metadata inside another app's container, which macOS protects; a custom npm cache, pnpm `store-dir`, `CARGO_HOME`, `GRADLE_USER_HOME`, or pip cache location is not read; runtimes bundled inside an old Xcode (14 and earlier) are not listed, so its simulators may be counted as unavailable.

## Build and test

Requires macOS 14 or later. The package builds and tests with Command Line Tools or Xcode 26:

```sh
swift test --package-path native/system
swift run --package-path native/system SubsetSystem   # unbundled executable, for quick local runs
```

`System.xcodeproj` is generated by `ProjectGenerator.rb` (xcodeproj 1.27) from the same sources: the static `SystemCore` and `SystemProcesses` libraries, the `Subset System` app (scheme `SubsetSystem`), and the `SystemCoreTests` and `SystemProcessesTests` bundles, neither hosted by the app. Regenerate it after adding or removing a source file; generation is reproducible, and CI fails if the committed project differs. Regenerating replaces only `project.pbxproj` and the shared `SubsetSystem` scheme, so breakpoints, personal schemes and workspace state in `xcuserdata` stay; `Tests/project-generator.sh` checks that. The generator needs exactly xcodeproj 1.27.0:

```sh
gem install --user-install xcodeproj -v 1.27.0
cd native/system
ruby ProjectGenerator.rb
xcodebuild -project System.xcodeproj -scheme SubsetSystem -destination 'platform=macOS' \
  CODE_SIGNING_ALLOWED=NO build test
```

The app is `LSUIElement` (menu bar only, no Dock icon), runs with the hardened runtime, and has no App Sandbox. `MacApp/SubsetSystem.entitlements` is intentionally empty. There is no privileged helper or telemetry, and System makes no network connection; it runs the local `docker` CLI only against a socket on this Mac (see Container VMs), for the containers and for `docker system df`, and `/usr/bin/tmutil listlocalsnapshots` for the volume summary. `MARKETING_VERSION` is 0.1.0; there is no app icon yet.

`.github/workflows/system.yml` runs on macOS 26 for changes here: package tests, the generated-project check, and an unsigned `xcodebuild build test`. Both test runs include live checks that sample the test process itself and this Mac's memory, scan fixtures in a temporary folder, and read this Mac's volume summary. `macos-release.json` describes the app for `scripts/release-macos.mjs` (see [docs/macos-release.md](../../docs/macos-release.md)), but System is kept out of beta builds until its signed build is accepted in [SET-59](https://linear.app/21n/issue/SET-59): `scripts/beta-builds.mjs` lists `macos/system` in `betaOptOuts`, so the **Beta builds** workflow never tags or builds it, even when it is named in `only`. SET-59 removes that entry.
