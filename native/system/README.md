# System (macOS)

System is a menu-bar app that will show where a Mac's CPU, memory, and disk space go, grouped by **origin** rather than as a flat process list: the app a helper belongs to, what launched it, the project a dev server runs in, and the containers inside a Docker-compatible VM. It is a Subset capability in the `planned` state.

This folder holds the app shell ([SET-39](https://linear.app/21n/issue/SET-39)) of the System outcome ([SET-38](https://linear.app/21n/issue/SET-38)), its process sampling ([SET-40](https://linear.app/21n/issue/SET-40)), the origin signals read for each process ([SET-41](https://linear.app/21n/issue/SET-41)), the attribution of processes to origins ([SET-42](https://linear.app/21n/issue/SET-42)), and the breakdown of Docker-compatible VMs into containers and compose projects ([SET-43](https://linear.app/21n/issue/SET-43)): a menu-bar app that shows total CPU and memory pressure, a temporary process table in the main window with each process's raw origin signals and, above it, each running container VM with its containers, an empty Settings window, a testable `SystemCore` package with the attribution rules, a generated Xcode project, and macOS CI. The app does not show origin groups yet (SET-44), scan disks, run cleanups, call AI providers, or ship the agent helper; those are SET-44 through SET-52.

## Capability boundary

**User outcome:** understand which app, tool, project, or container is using CPU, memory, and disk space, and reclaim space safely.

**Sources of truth:**

| Data | Source | Issue |
| --- | --- | --- |

Samples and scan results stay in memory; there is no persisted history. All measurement and attribution are deterministic. Optional AI explanations (on-device Apple Intelligence or the user's own OpenRouter key, SET-49 to SET-51) never measure, group authoritatively, or trigger a cleanup.

## Process sampling

`ProcessSource.sample()` reads every visible process once. `LibprocProcessSource` lists PIDs with `proc_listallpids` and reads, per process, `PROC_PIDTBSDINFO` (parent, effective user, start time, name), `proc_pidpath`, and `proc_pid_rusage(RUSAGE_INFO_V6)` (`ri_phys_footprint`, user and system CPU time, `ri_energy_nj`, `ri_billed_energy`). For another user's process, whose `PROC_PIDTBSDINFO` macOS denies, the start time, parent, owner and name come from `kinfo_proc`. The kernel holds a name in a fixed-width buffer (31 bytes in `pbi_name`, 16 in `p_comm`), so the executable's file name is shown instead when the kernel name is empty or a strict prefix of it; any other kernel name is kept. `FixtureProcessSource` replays recorded samples for tests. Command-line arguments are never read, since they can hold secrets; only the executable path is.

- **Identity** is `(pid, startTime)`, so a PID the kernel reuses is a new process. macOS refuses `PROC_PIDTBSDINFO` for another user's process; the identity, parent and owner then come from the process table (`sysctl` `KERN_PROC_PID`), which is readable for every process.
- **Restricted processes.** Without root, `proc_pid_rusage` fails with `EPERM` for other users' processes (about a quarter of them on the development Mac). They stay in the snapshot with `restricted = true` and `nil` usage values, never zero. Any other read failure also leaves the values `nil`, without `restricted`. A process that exits mid-read is left out. The reads are keyed by PID alone, so the start time is read again after them; if the PID changed hands meanwhile, the process is read once more, and left for the next sample if it changes hands again.
- **Units.** CPU times arrive in Mach absolute time units and are converted with `mach_timebase_info` (125/3 ns per tick on Apple silicon). Memory is the physical footprint, the figure Activity Monitor shows as Memory. Energy (`energy`, from `ri_energy_nj`) is the nanojoules the process's own work has used since it started; the table shows it as Energy Used. `billedEnergy` (`ri_billed_energy`) is a different figure: nanojoules billed to the process for work other processes did on its behalf, usually far below its own energy, so nothing presents it as the process's energy use.
- **CPU %** is the CPU time delta of one identity over the uptime delta between two samples, with 100% meaning one fully used logical core (Activity Monitor's convention). A process's first sample, including a process that reused a PID, has no CPU value; a process that exited is dropped.
- **Machine CPU**, the figure the menu bar shows, is the busy share of all cores between two samples from `host_statistics(HOST_CPU_LOAD_INFO)` tick deltas, which any user may read, so it includes restricted processes that the per-process figures miss. It is unavailable on the first sample, after a failed tick read, and for the one interval in which a 32-bit counter wraps or resets. The menu bar says CPU is not measured yet only before the second sample and unavailable for any later interval without a figure; while sampling fails, it says unavailable rather than showing the last figure.
- **System memory** (`SystemMemory`): pressure level from `kern.memorystatus_vm_pressure_level` (normal, warning, critical), swap used and total from `vm.swapusage`, physical memory from `hw.memsize`, and app (anonymous minus purgeable), wired, and compressed memory from `host_statistics64(HOST_VM_INFO64)`. A missing or malformed value is `nil`.
- **Cadence.** Every 2 seconds while the main window is visible on screen, every 10 seconds otherwise. A change applies at once, but a sample never starts while another runs or sooner than the new interval after the previous one started. Samples stay in memory; there is no history.

Agreement with Activity Monitor on a real workload is checked in SET-53, not here.

## Origin signals

`OriginSignalReader` (`Core/Signals/`) reads the signals macOS gives a non-root user about where a process came from, once per process identity, and stores them in `ProcessFacts.origin`. SET-42 groups processes from them. Each signal is a value or an `unavailable` reason, and names the interface (`SignalSource`) that supplied it either way. The convenience fields `responsiblePID`, `coalitionID`, `teamID`, `signingID`, `isPlatformBinary`, `launchdLabel`, `workingDirectory`, and `tty` are the bare values (`launchdLabel` only when `launchdMatch` identifies a job, below), `nil` when unavailable or not read yet.

| Signal | Reader and source | Without root |
| --- | --- | --- |
| Responsible process | The private `responsibility_get_pid_responsible_for_pid`, resolved with `dlsym` | Own processes only; others are `denied` |
| Coalition ID | The private `PROC_PIDCOALITIONINFO` flavor (20) of `proc_pidinfo`, resolved with `dlsym`; the resource coalition | Every process |
| Code signature: signing identifier, Team ID and the team's name from the leaf certificate's common name, Apple platform binary | `SecCodeCopyGuestWithAttributes` by PID, then `SecCodeCopySigningInformation`, published once `SecCodeCheckValidity` (without network access) finds the running code matches the file and the kernel's status of the running code (`kSecCodeInfoStatus`) agrees that it is signed, or both are unsigned | Every process; one whose file was replaced since it started (an app updated while it runs, or a signed program replaced by an unsigned file) is `unavailable` |
| launchd jobs: label, plist, domain, `orphaned` | An index of `~/Library/LaunchAgents`, `/Library/LaunchAgents`, `/Library/LaunchDaemons`, and `Contents/Library/LaunchAgents` in each app in `/Applications` and `~/Applications` | Every readable plist; an unreadable plist or an unchecked program is recorded and carried with the jobs found, and a process with no job found then reads `incompleteScan` |
| Working directory | `PROC_PIDVNODEPATHINFO` | Own processes only |
| Controlling terminal | `e_tdev` from `PROC_PIDTBSDINFO`, else from the process table (`sysctl` `KERN_PROC_PID`) | Every process |

- **Private interfaces.** The owner approved the two private interfaces. Each adapter reports `symbolMissing` when its symbol is absent and the call's `errno` (`denied`, `processExited`, or the code) when it fails, so grouping can fall back to the bundle path and parent chain. Neither is linked directly, so a macOS without them still launches.
- **Partial results.** Each reader is independent: a restricted process keeps the signals that succeed (on the development Mac, other users' processes kept their coalition, terminal, and, where the kernel reports an executable path, signature) and records a reason for each that does not.
- **Once per identity and executable.** Results are cached by `(pid, startTime)` and the executable path, and dropped when the process exits. `exec` keeps the PID and start time but replaces the executable (a shell wrapper that runs `exec node server.js`, say), so a process that reappears with another executable path is read again and its signature, launchd jobs, and match follow the new executable. The reads are keyed by PID, so the process is checked afterwards: if the PID changed hands meanwhile, the signals are discarded and recorded as `processExited`; if it now runs another executable, they are discarded and the process stays "not read yet" until the next sample reads its new executable. Reading all of a Mac's processes the first time takes seconds (about 6.7 s for 733 processes on the development Mac, mostly in the Security framework), so one sample reads new identities, oldest first, for at most one second; the rest stay `nil` ("not read yet") until a later sample.
- **Signature cache.** Signatures are cached by executable path, file size, and modification time, plus the status-change time, which the kernel always sets even when an installer preserves an older modification time. The many processes running one executable cost one read, and a rebuilt or updated file is read again. Signatures are read by PID, so a read fills the cache only when it must describe the file as stamped: the process started after the file last changed, the file did not change during the read, and afterwards the PID still belongs to the same process and that process still runs the file (a process that ran `exec` during the read would otherwise file its new executable's signature under the old path). A process started before its file changed may run the replaced version, and one that no longer runs the file when an entry would answer for it is checked first, so either is read directly and neither uses nor fills the entry. The signing information itself comes from the file on disk, so every read is checked against the running code first: a process whose file was replaced (on the development Mac, helpers of an app updated while they ran) reads `unavailable`, not the replacement's identifier and Team ID. An unsigned file cannot be compared with the running code, so it is read as unsigned only when the kernel reports the running code unsigned too; signed code whose file was replaced by an unsigned one, or the converse, reads `unavailable`. Failures are not cached. The cache starts over past 4,096 paths.
- **launchd index.** A job's program is `Program`, which must be an absolute path, else `BundleProgram` (relative to its app bundle), else `ProgramArguments[0]`, which launchd resolves like `execvp` against `/usr/bin:/bin:/usr/sbin:/sbin`. Symlinks are resolved, because the kernel reports a process by its real path (Homebrew services name a symlink). A plist whose program does not exist (`ENOENT`, `ENOTDIR`, `ELOOP`, or not a regular file) is kept as `orphaned`. A program whose path cannot be checked for another reason, such as one under a root-only folder (`EACCES`), is `unchecked`, not orphaned, and is recorded in `scanFailures` with its location and `errno` like an unreadable plist below; for a bare name, only when no `PATH` entry has it and one could not be checked. A plist without a label or program, with a relative `Program`, that does not parse, or that is not a regular file (a folder, FIFO, or device named `.plist`, or a symlink to one; plists are opened without blocking, so a FIFO cannot stall sampling) is listed as unreadable, since launchd cannot load it either. A folder or plist that exists but cannot be read (no read permission, or a plist over 1 MiB, which is not read into memory and is recorded as `EFBIG`; a missing folder is fine) is recorded in `scanFailures` with its `errno`, because launchd, running as root, may still load a job from it: a process whose executable no readable plist names then gets `launchdJobs` `unavailable` with an `incompleteScan` reason naming each failure, not an empty list, and jobs that were found are still returned with the failures in `LaunchdJobs.scanFailures` (the detail view lists them under the jobs). Some Macs have such a plist (the development Mac has a mode 700 root-only one in `/Library/LaunchDaemons`), and there every process without a found job reads as an incomplete scan. Apps are looked for in `/Applications` and `~/Applications` and up to two folder levels below them (`/Applications/Utilities`, a vendor's folder), not inside other bundles and not through symlinked folders. On every sample (about 2.6 ms for 61 jobs on the development Mac), the plists are read again if any plist, plist folder, or application folder appeared, disappeared, changed size, modification time, or status-change time (so a permission fix counts), or could or could no longer be read, and every program is resolved again, so a program that is deleted, created, has its symlink retargeted (as `brew upgrade` does to `/opt/homebrew/opt`), or becomes checkable after a permission fix is followed without a plist change. When the index changes, every process already read looks its executable up again, so a plist added, edited, removed, or made unreadable reaches processes that are already running. Apple's `/System/Library` jobs are not indexed; their programs are platform binaries.
- **launchd match.** A plist names a program, not a process, so `origin.launchdJobs` lists every plist naming the executable and `launchdMatch` says whether they identify the process's own job. It is `job(label:)`, and `launchdLabel` is set, only when the executable is not an Apple platform binary, the parent is launchd (pid 1), every matching plist has the same label, and every plist was read. Otherwise it is `executableOnly` with the first reason that applies: `sharedExecutable` (a platform binary such as `/bin/sh`, `/usr/bin/env`, `/usr/bin/osascript`, or `/usr/bin/sandbox-exec`, which any job or user may run, or a signature that could not be read), `notStartedByLaunchd` (a terminal or app started this copy), `conflictingLabels`, or `incompleteScan` (a plist or program that could not be read may name the executable with another label). So on a Mac with an unreadable plist, such as the development Mac, `launchdLabel` is never set, and SET-42 groups processes from the bundle path and parent chain instead. A process whose parent exited is reparented to launchd too, so `job` is the plists' claim, not launchd's; root-only `launchctl procinfo` would confirm it and is out of scope.
- **Not read:** command-line arguments (they can hold secrets) and root-only sources such as `launchctl procinfo`.

The live tests read the test process's own working directory, terminal state, and code signature, launchd's (pid 1) signature and restricted reads, and record whatever the two private interfaces return. Whether the signals are right for real apps, agents, and dev servers is checked on a working Mac in SET-53.

## Origin attribution

`Attribution` (`Core/Attribution/`) takes one sample's `[ProcessFacts]`, every indexed launchd job (`LaunchdJobIndex.jobs`), a project-marker lookup, and a mount table, and places every process in exactly one group in each of four layers. Each placement (`ProcessAttribution`) names the group, the rule that placed it, a confidence (`rule`, `signal`, or `fallback`), and the evidence used. It reads nothing but the marker lookup and the mount table, so the same inputs always give the same groups. Real-workload agreement is checked in SET-53, not here; misattributions outside the rules below are SET-61 follow-ups.

**App layer.** A closed rule set; the first rule that matches places the process:

| # | Rule | Group | Confidence |
| --- | --- | --- | --- |
| 1 | The executable is inside an outermost `*.app` bundle: a `.app` path component followed by `Contents` (or an iOS app's `Wrapper`), so a folder merely named `x.app` does not count. Helpers, XPC services, login items, and a terminal app's own processes. | The app, by bundle path, shown with the bundle's file name | rule |
| 2 | An Apple platform binary under `/System`, `/usr/libexec`, `/usr/sbin`, `/usr/bin`, or `/sbin`. A signature that is not yet read does not contradict a location on the sealed system volume, which holds only Apple's files. The writable, unsealed locations among them need a platform signature: the volumes under `/System/Volumes` (Data, Preboot, …) and the Data-volume folders that `/usr/share/firmlinks` links in (`/usr/libexec/cups`, and `Caches`, `Assets`, `AssetsV2`, `PreinstalledAssets`, `PreinstalledAssetsV2`, `Speech`, and `CoreServices/CoreTypes.bundle/Contents/Library` under `/System/Library`). A signature that says it is not a platform binary contradicts any location. | macOS, sub-grouped by launchd label when known | rule |
| 3 | A container VM's process, from `ContainerVMRecognizer` (see Container VMs). Its processes run inside the runtime's app bundle or are Apple's Virtualization.framework service under `/System`, so a process it claims is placed here even when rule 1 or 2 also matches. | The runtime: Docker Desktop, OrbStack, or Colima | rule |
| 4 | The process or an ancestor runs a coding agent: `claude`, `codex`, `cursor-agent`, `droid`, `opencode`, `amp`, or `gemini`, as the kernel's process name, the executable's file name, or the agent folder of a versioned install (`…/claude/versions/2.1.304`, the layout of Claude Code's native installer, whose kernel name is the version). The agent's own process counts, so the agent's footprint is in its group. | "Agent: \<name\>", sub-grouped by project | rule |
| 5 | A strict ancestor runs a known terminal app (bundle `Terminal.app`, `iTerm.app`, `Ghostty.app`, `Warp.app`, `WezTerm.app`, `kitty.app`, `Alacritty.app`, `Visual Studio Code.app`, or `Cursor.app`). VS Code and Cursor also start language servers and other tools, so under them only a process with a controlling terminal is in the integrated terminal. | Terminal, sub-grouped by project | rule |
| 6 | The responsible process, else the coalition's earliest-started member (its leader, as far as a non-root reader can tell), is another process inside an app bundle. A responsible PID that belongs to a process started later than this one was reused and is ignored. | That app | signal |
| 7 | `launchdLabel` is set (`LaunchdMatch.job`) and its plist is in an app bundle's `Contents/Library/LaunchAgents` (that app) or the executable has a Team ID (that team). A job with neither falls through, so a Homebrew service reaches rule 8. | The app or team | signal |
| 8 | The executable is under `/opt/homebrew` or `/usr/local/Cellar`. The formula is the folder after `Cellar`, `opt`, or `Caskroom`. | "Homebrew: \<formula\>", or "Homebrew" | rule |
| 9 | The signature has a Team ID. | The team, shown with its name from the signing certificate (`CodeSignature.teamName`, such as "Google LLC") or "Team \<ID\>" | signal |
| 10 | Nothing matched. | The executable path, or the process name without one | fallback |

Later rules that also match are evaluated too (for a container VM, rules 1 and 2 as well), and one that names a different origin than the winner is recorded in `Placement.conflicts` with its evidence; it never changes the placement. The responsible process, the coalition leader, and a launchd job's owning app (rules 6 and 7) name an app, so any other group disagrees with them: a dev server whose responsible process is Terminal stays in Terminal, with Terminal.app recorded. A Team ID (rule 9, or rule 7 for a job outside an app bundle) names who signed the code, so it is recorded when the winner names no signer (macOS, a container VM, an agent, a terminal, or Homebrew), such as a signed tool run in a terminal, and not when the winner is an app bundle, which is that signed code, or an app found through rule 6 or 7. A Homebrew path only restates the executable's location and is never a conflict. A container VM found through its runtime's app bundle is that app: the app named by a responsible process, coalition leader, or launchd job agrees with it, and so does the Team ID of a process inside that bundle.

**Other layers.**

- **Vendor:** Apple (platform binary), the Team ID (named from the certificate when it names the team), unsigned (no Team ID; ad hoc signatures such as Homebrew's included), or signature unavailable. An unread or unreadable signature is never reported as unsigned.
- **Launch source:** the parent's coding agent ("Coding agent: \<name\>"; the agent's own process was started by whatever started the agent), else a terminal session (rule 5's test), else the nearest of the process and its ancestors that has a launchd label (the label), is a login item (`Contents/Library/LoginItems` inside an app), is inside an app bundle or has an app as its responsible process ("Launched by an app"), or has launchd as its parent ("System"). A chain that ends at a parent missing from the sample is "System" with `fallback` confidence and the missing PID as evidence. On a Mac with an unreadable launchd plist (see Origin signals) no process has a label, so launch agents show as System or as launched by an app.
- **Project:** the nearest folder at or above the working directory holding `.git`, `package.json`, `Cargo.toml`, `go.mod`, `pyproject.toml`, `Package.swift`, `Gemfile`, or `pom.xml` (looked for in that order, with `lstat`, once per folder per call, `/` included), else the working directory itself (`/` too), else no project when the working directory is unavailable. Markers are looked for only on local volumes: the mount table is read once per call with `getmntinfo_r_np(MNT_NOWAIT)`, which asks no file system and fills a buffer owned by that call (plain `getmntinfo` shares one buffer across the process, so concurrent calls could overwrite or free it), and the walk stops at the first folder on a volume without `MNT_LOCAL` (SMB, NFS, AFP, most FUSE volumes), whose `lstat` can hang. Such a process's project is its working directory, with the skipped volume as evidence. The working directory is readable only for the user's own processes.

**Totals.** Each group and subgroup sums its members: memory (`physFootprint`, marked `isApproximate` because shared pages count once per member), CPU percent, and energy, which is the billed energy (`ri_billed_energy`) as SET-42 specifies. Billed energy covers work other processes did on the members' behalf and is usually far below their own use (see Units), so the members' own energy (`ri_energy_nj`) is summed separately as `ownEnergy`. Each figure counts measured and unmeasured members, and `restrictedCount` counts restricted members separately; a member without a value is never added as zero, and a group with no measured member has no sum. Sums saturate rather than overflow.

**Identity and cost.** A group's `OriginGroupID` is built from paths, labels, Team IDs, and names, never PIDs, so it is the same in every sample and the UI can keep expansion and selection. Groups are ordered by identity and members keep the order they were given. A parent index is built once per call and each ancestor question (nearest agent, nearest terminal, inherited launch source) is answered for the whole sample at once, so attribution is linear in the number of processes; the 2,000-process test checks the step count on a 2,000-deep chain, where a walk per process would follow about two million links.

**Known limits** (SET-53 checks real workloads; SET-61 collects follow-ups):

- Rule 2 precedes rules 4 and 5, so `/usr/bin` tools started from a terminal or agent (`/usr/bin/login`, `/usr/bin/git`, `/usr/bin/python3`) are macOS, and Apple binaries outside the rule's locations, such as `/bin/zsh` outside any terminal or agent, are unattributed.
- A platform binary never gets a launchd label from SET-41's signals (`LaunchdMatch.sharedExecutable`, and Apple's own jobs are not indexed), so the macOS group has no label subgroups yet.
- The coalition leader is the earliest-started member in the sample; macOS does not tell a non-root reader which member leads.
- Rule 1 takes the outermost `*.app` wherever it is, so a process run from an app bundle nested in a framework or Homebrew keg (framework Python's `Python.framework/…/Resources/Python.app`) joins that app's group, even a dev server in a terminal or agent session.
- Terminal and agent subgroups use the process's own project; a process whose working directory cannot be read (another user's) is in the group but in no subgroup.
- Working directories inside app bundles and app containers (an XPC service's bundle folder, `~/Library/Containers/…/Data`) become projects of their own under the "working directory itself" rule.
- A working directory on a network or FUSE volume, or in a local volume mounted inside one, never finds a marker on that volume, so a repository on a network share is grouped by its working directory rather than its root.
- The live marker lookup stats files in each working directory's folders. In a folder macOS protects (Documents, Desktop, Downloads), that may need the user's permission; the app does not run attribution yet, and its on-screen behavior is checked in SET-44 and SET-53.

The fixture tests record one process per rule (Chrome renderer helpers, an XPC service and login item, an Apple daemon and an unsigned binary on a writable system volume, a container VM through a stand-in recognizer and through `ContainerVMRecognizer` (ContainerVMTests), `node` under `claude` under `zsh` under Ghostty, a dev server in Terminal and in VS Code's integrated terminal, an app found through its responsible process and coalition, a launch agent with an orphaned plist of the same label, a Homebrew service and its workers, a signed tool, an unsigned binary), the precedence between conflicting signals and which of them are recorded as conflicts, the project walk through `/` and its stop at a network volume, totals with restricted members, group identity across two samples, and the linear-time bound. A live test attributes this Mac's processes and checks that each is placed once per layer.

## Container VMs

When Docker Desktop, OrbStack, or Colima runs, its processes form one origin group (App rule 3) with what macOS measures for them, and beneath it the containers and compose projects the runtime's own CLI reports from inside the VM. The two figures are shown side by side and never reconciled: the VM reserves memory that its containers may not use, and the containers' figures come from the Linux kernel inside the VM.

**Recognizing the VM** (`ContainerVMRecognizer`, `Core/Containers/`). A closed rule set over one sample; the first that applies places a process:

| # | Rule | Runtime |
| --- | --- | --- |
| 1 | The executable is inside an outermost `Docker.app` or `OrbStack.app` bundle and is not a client (below): the UI, backend, helpers, and Docker Desktop's bundled QEMU or hypervisor | Docker Desktop, OrbStack |
| 2 | Lima's host agent, `limactl` whose parent is launchd or another `limactl` (`limactl start` runs it, then exits), or Colima's daemon, `colima` whose parent is launchd (`brew services`, `colima daemon`), by file name or kernel name | Colima |
| 3 | A process outside any app bundle with an ancestor placed by rule 1 or 2: what the runtime started, such as `qemu-system-*`, `ssh` port forwarders, and `socket_vmnet` under Lima's host agent | That ancestor's |
| 4 | Apple's Virtualization.framework VM service (`com.apple.Virtualization.VirtualMachine`), which launchd starts for a runtime: the runtime of its responsible process, else the one runtime among the other members of its coalition (Colima started in Terminal has Terminal as the VM's responsible process, in a coalition shared with Lima's host agent) | That process's |

Only the VM and daemon side counts, so only it creates a group and starts a poll. A client is not the VM: the `docker` CLI (`Docker.app/Contents/Resources/bin/docker` is what `/usr/local/bin/docker` usually links to, and OrbStack's `xbin/docker` what `~/.orbstack/bin/docker` links to), `docker-*` credential helpers and anything in a `cli-plugins` folder, `kubectl`, `hub-tool`, `com.docker.cli`, and OrbStack's `orb` and `orbctl`. Neither is a `limactl` or `colima` command run from a shell or by `colima` (`colima start`, `limactl list`). These, including System's own `docker` child, are placed by the other App rules: a client inside an app bundle stays with that app (rule 1), and a command run in a terminal with that terminal session.

A responsible PID that belongs to a process started later than the VM service was reused and is ignored. A coalition holding two runtimes leaves the VM service unrecognized, and it stays in macOS. So does a coalition with more VM services than its runtime runs: one for Docker Desktop or OrbStack, and one per Lima host agent that does not run QEMU for Colima, so a tart or vfkit VM started in the same terminal as Colima is not counted as Colima's. `ContainerVMRecognizer.groups(in:)` gives each running runtime's members and totals (`GroupTotals`) without the rest of attribution, so the app needs no project-marker lookups to show them.

**Asking the runtime** (`DockerCLI`). Only a `docker` executable at one of these paths, tried in order, is run: `/usr/local/bin/docker`, `/opt/homebrew/bin/docker`, `~/.orbstack/bin/docker`, `/Applications/Docker.app/Contents/Resources/bin/docker`; never one found through `PATH`. It runs without a shell, with only `HOME` and a fixed `PATH` in its environment, so `DOCKER_HOST`, `DOCKER_CONTEXT`, and `DOCKER_CONFIG` cannot redirect it. Before it runs, the current context is read the way the CLI reads it: `currentContext` in `~/.docker/config.json`, whose endpoint is in `~/.docker/contexts/meta/<sha256 of the name>/meta.json`; no context, or `default`, is `unix:///var/run/docker.sock`. An endpoint that is not a `unix://` socket (`ssh://`, `tcp://`) is a remote context and the CLI is not run. The socket's real path names the runtime (`~/.docker/run/docker.sock` Docker Desktop, `~/.orbstack/run/docker.sock` OrbStack, `docker.sock` in a profile folder under `~/.colima` or `~/.config/colima` Colima), and only that runtime's group shows the breakdown; another running runtime says which one the context reaches. A socket that names no runtime is taken to be the only running runtime's, else no group gets the breakdown.

It then runs `docker --host <that endpoint> ps --format '{{json .}}'` and `docker --host <that endpoint> stats --no-stream --format '{{json .}}'`. Pinning the endpoint keeps both commands on the socket that was checked, even if the current context changes during the poll, and the report names that endpoint. Each has a 5-second timeout, past which the command is stopped (`SIGTERM`, then `SIGKILL` a second later) and the report says so at once. Output is read as it arrives and capped at 8 MiB.

**Cadence.** `ContainerPoller` runs the two commands at most once every 10 seconds, only while the main window is visible and a runtime's VM is running, and never twice at once. With only the menu bar in use it never runs. Hiding the main window cancels a poll in progress: the running command is stopped the same way and no further one starts. The poll runs beside the sampling loop and never delays a sample.

**Reading the output** (`DockerOutput`, `ContainerBreakdown`). Each line is one JSON object. `docker ps` gives the ID, the first name, the image, and the `com.docker.compose.project` label from `Labels` (a compose project name never holds a comma, so splitting the labels on commas is safe); `docker stats` gives `CPUPerc` (percent of one virtual core, so it can pass 100) and `MemUsage` (`used / limit`). Sizes use the CLI's binary units (`B`, `KiB`, `MiB`, `GiB`, `TiB`, `PiB`) or decimal ones (`kB`, `MB`, `GB`, `TB`, `PB`). The two lists are joined by ID (one may be a prefix of the other), and by name only for a row without an ID. Two rows with different IDs are different containers even when they share a name (one recreated between the commands). A container in only one of the lists is kept, without usage or without labels. Containers are sub-grouped by compose project, with standalone containers after. The CLI's `--` placeholder is unmeasured, not zero. A line that is not a JSON object with an `ID` is skipped and counted (`skippedLines`), and a value that is not a number with a known unit is left `nil` and counted (`unreadableValues`); the view shows both counts.

**No breakdown.** The VM group stays without containers and shows the reason when no CLI is at a candidate path, the context cannot be read or is remote, the daemon is not running (the CLI's "Cannot connect to the Docker daemon", or "failed to connect to the docker API" from Docker CLI 28 and later), a command times out, fails with another exit status (its first error line is shown), cannot be started, prints more than the cap, or prints lines none of which can be read. Empty output is a running daemon with no containers.

**Known limits** (a real runtime is checked in SET-53): a plain Lima VM is shown as Colima, since both run `limactl`; Kubernetes, Podman, remote contexts, and starting, stopping, or pruning containers are out of scope; whether the VM service's responsible process and coalition are as described for each runtime is verified on a real Mac in SET-53. Without a process's arguments, the coalition fallback matches VM services to host agents by count, not by which VM each one runs: if Colima's own VM service is in another coalition, another tool's VM in the host agent's coalition is counted as Colima's. The client names and the launchd-parent rule for `limactl` and `colima` are also checked against each runtime's real layout in SET-53.

The tests use recorded `docker ps` and `docker stats` lines (parsing, compose grouping, units, malformed lines), a stub `docker` script (success, the endpoint pinned across a context change, the environment it runs with, timeout, a stopped daemon in both CLI wordings, another failure, unreadable output, a missing or non-executable binary, a remote context, runaway output, the stub's process gone after a timeout, the cap, or a cancellation, the 10-second limit, the menu-bar-only rule, hiding the window during a slow `docker ps`, and overlapping polls), and process fixtures for Docker Desktop, OrbStack, Colima with `vz`, with QEMU, and under `brew services`, the clients and transient commands that are not the VM, coalitions with more VM services than Colima runs, and the VMs the recognizer must leave alone (UTM, QEMU run by hand, Podman).

## Build and test

Requires macOS 14 or later. The package builds and tests with Command Line Tools or Xcode 26:

```sh
swift test --package-path native/system
swift run --package-path native/system SubsetSystem   # unbundled executable, for quick local runs
```

`System.xcodeproj` is generated by `ProjectGenerator.rb` (xcodeproj 1.27) from the same sources: a static `SystemCore` library, the `Subset System` app (scheme `SubsetSystem`), and the `SystemCoreTests` bundle. Regenerate it after adding or removing a source file; generation is reproducible, and CI fails if the committed project differs. Regenerating replaces only `project.pbxproj` and the shared `SubsetSystem` scheme, so breakpoints, personal schemes and workspace state in `xcuserdata` stay; `Tests/project-generator.sh` checks that. The generator needs exactly xcodeproj 1.27.0:

```sh
gem install --user-install xcodeproj -v 1.27.0
cd native/system
ruby ProjectGenerator.rb
xcodebuild -project System.xcodeproj -scheme SubsetSystem -destination 'platform=macOS' \
  CODE_SIGNING_ALLOWED=NO build test
```

The app is `LSUIElement` (menu bar only, no Dock icon), runs with the hardened runtime, and has no App Sandbox. `MacApp/SubsetSystem.entitlements` is intentionally empty. There is no privileged helper or telemetry, and System makes no network connection; it runs the local `docker` CLI only against a socket on this Mac (see Container VMs). `MARKETING_VERSION` is 0.1.0; there is no app icon yet.

`.github/workflows/system.yml` runs on macOS 26 for changes here: package tests, the generated-project check, and an unsigned `xcodebuild build test`. Both test runs include live checks that sample the test process itself and this Mac's memory. `macos-release.json` describes the app for `scripts/release-macos.mjs` (see [docs/macos-release.md](../../docs/macos-release.md)), but System is kept out of beta builds until its signed build is accepted in [SET-59](https://linear.app/21n/issue/SET-59): `scripts/beta-builds.mjs` lists `macos/system` in `betaOptOuts`, so the **Beta builds** workflow never tags or builds it, even when it is named in `only`. SET-59 removes that entry.
